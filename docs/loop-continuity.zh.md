# 按证据续跑

[English](loop-continuity.md) · [文档索引](README.md) · [执行契约](../references/exec.md)

自动续跑最容易误判两件事：把变化的日志当成进展，或在还能推进时因为轮数用完而停下。Spec Harness 的 `main` 用真实的验证记录决定下一步。这一机制不在 `v2.2.0` 发布包中。

## 继续、换路还是停下

| 验证结果 | 下一步 |
| --- | --- |
| 验证通过并产生有效检查点 | 推进已就绪任务；都完成后，运行 `spec.py check` 复验最终交付树。 |
| 同一任务和命令失败，但已验证的代码树和失败诊断都是第一次出现 | 可以请求续跑。换一个能验证的假设或实现，也可先做独立任务。 |
| 代码没变、只有日志变了，或回到了已经试过的代码树或失败诊断 | 不用这次失败开启下一轮。重复回调和只读预检也不算新证据。 |
| 只剩阻塞任务，或下一步需要授权 | 结束自动续跑；保留证据和未决项。有独立就绪任务时先做独立任务。 |

比如，方案 A 和 B 各自带来新的失败诊断，值得分别调查；B 不奏效，又退回 A 时，即使日志里的时间戳变了，也不值得再开一轮。失败签名忽略常见的运行噪声，但保留不同退出码，并区分进程自己返回 `124` 和实际超时。

重规划改的是**下一步做法**，不是目标。提示会带上冻结目标、受影响的验收条件和证据账本的位置。不能为了通过验证降低验收标准，修改计划仍须走有授权的 `plan-amend`。Stop 没有全局轮数配额；[单任务验证门禁](../references/exec.md#failure-ladder)仍在，手动 `check` 不受 Stop 限制。

## Loop Transformer 启发了什么

[Huginn 的循环深度研究](https://arxiv.org/abs/2502.05171)在模型内部反复运行同一组层。每轮仍以原始输入为条件；论文用相邻两次预测分布的差异作为提前退出的信号。

Spec Harness 借鉴的是**保留原目标、观察每轮是否产生新信息、据此决定何时停止**。对应的信号是实跑验证、代码树和失败签名，不是模型内部状态或概率。它没有集成或训练 Huginn，也不据此声称节省了模型 token。这与早期从 `dsh-purge` 借鉴的会话恢复线索是两回事；没有采用其审批或沙箱改写。

## 宿主与手动恢复

Pi 通过 `agent_before_settle` 请求继续；Claude 风格的 Stop 适配器在重入时也要求新证据。Cursor 只在需要继续时发 follow-up，不会用“已停止”的提示开启下一轮。其他宿主是否能自动续跑取决于实际事件和桥接支持，安装了配置不代表事件已加载或触发。

没有自动回调时，在绑定的工作区运行 `spec.py next` 查看下一步，修复后再运行同一个 `spec.py check`。`runs.jsonl` 是真实执行记录，`state.json` 只提供简报或恢复线索。想核对行为，可读 [续跑回归用例](../tests/test_convergence_hooks.py)：它们覆盖第七轮仍可推进、同一代码树输出变化、A→B→A 循环，以及真实调度器的重入处理；这些是离线测试，不是模型效果基准。
