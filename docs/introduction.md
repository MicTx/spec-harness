# Spec Harness：让 AI 编程从“会写代码”走向“能完成任务”

AI 编程工具已经能在几分钟内生成一段可运行的代码。真正困难的部分通常更长：目标会不会在多轮对话后变形，改动能不能被别人复核，验证是否真的覆盖了需求，几天后能不能从上次停下的地方继续。

Spec Harness 是一个面向 AI 编程的规范驱动工作流 Skill。它把一次复杂开发工作放进一个可读、可验证、可恢复的任务包里，让 AI 学习者、编程者、Agent 开发者和长程任务开发者都能看到同一条证据链：

    goal → scope → tasks → verify → archive → commit → push

它不提供模型，也不运营托管服务。它提供的是一套让模型和人都不容易忘记“正在解决什么、改了什么、如何证明”的工作面。

## 你真正缺的，通常不是另一段代码

设想一个简单的请求：给已有服务增加审计日志导出。

第一轮对话可以很顺利。Agent 找到一个路由，写入一个导出函数，再补几条测试。问题从第二轮开始出现：

- 需求里“审计日志”到底包括哪些事件？
- 导出接口可以修改哪些文件，不能碰哪些数据？
- 测试通过的是导出函数，还是用户真正调用的接口？
- 中途换了一个 Agent，谁知道已经做过什么？
- 代码合并后，任务是否真的完成，还是只完成了“看起来像完成”的部分？

Git 能记录文件，测试能记录命令，聊天记录能记录讨论，但它们各自只保存一部分答案。长程开发需要把这些答案绑在一起。

这就是 Spec Harness 的切入点：它不替你选择业务方案，而是要求每个方案都留下可检查的范围、任务和证据。

## 任务包：给长期工作安一个可读的容器

一次 Spec Harness 任务包通常包含三个文件：

    .spec/specs/YYYY-MM-DD_slug/
    ├── spec.md
    ├── tasks.md
    └── checklist.md

它们各自回答一个问题。

### spec.md：我们到底要解决什么

这里写目标用户、已确认事实、关键假设、待确认问题、最小实现路径和明确的范围外内容。

范围不是形式。它是 Agent 的护栏。比如：

    本轮允许修改：导出 API、序列化模块和相关测试。
    本轮不修改：数据库迁移、用户权限模型和前端页面。

当后续对话提出“顺手把前端也重构一下”，你不必依靠记忆争论；范围文件已经给出答案。

### tasks.md：每一步怎样才算完成

每个任务都包含两个字段：

- boundary：这个任务允许改变什么。
- verify：完成后用什么实际验证证明它完成。

例如：

    - [ ] 增加审计导出接口
      - boundary: 只修改 API 路由、导出服务和接口测试
      - verify: 运行接口集成测试，并用临时数据核对导出内容

boundary 解决“改到哪里为止”，verify 解决“凭什么说做完了”。没有 verify 的复选框只是愿望；没有 boundary 的任务很容易膨胀成另一项工程。

### checklist.md：交付能不能被接受

任务完成不等于交付完成。清单还要检查文档同步、边界回归、构建、测试和必要的手工验证。

这三个文件之间形成一个小型契约：

    spec.md      定义问题和边界
    tasks.md     组织执行和验证
    checklist.md 判断交付是否可信

它们是文本文件，所以人可以读，Git 可以审查，脚本可以检查，Agent 也可以在新会话里恢复上下文。

## 四类读者，四种收益

### AI 学习者：把“我觉得对”换成“我能证明”

学习 Agent 编程时，最容易把输出长度误认为工作质量。任务包会迫使你区分三件事：

1. 目标是否理解正确。
2. 代码是否落在允许的范围内。
3. 验证是否真的覆盖了目标。

你可以从一个很小的任务开始：只改一个函数，给它写一个 boundary 和一个 verify。这个练习训练的是工程判断，而不只是提示词写法。

### 编程者：让工作树和提交有清楚的边界

Spec Harness 在 Git 仓库中为任务建立独立的 spec/ 分支，并把任务包、代码修改和提交关联起来。完成阶段归档任务包，提交阶段留下 Conventional Commit 和任务包标识，发布阶段再单独合并和推送。

这和普通 Git 分支很像，但侧重点不同：

- Git 分支回答“哪些对象一起变化”。
- 任务包回答“这些变化为什么属于同一个目标”。
- verify 证据回答“它们是否真的达到目标”。

三者结合后，审查者不必从几十个文件里猜这次提交解决了什么。

### Agent 开发者：把委派写成合同

Agent 之间传递上下文时，最危险的句子是“你去把这部分处理好”。它没有说清目标、范围、输出形状和验收方式。

Spec Harness 的委派合同要求每个独立工作单元都写清：

    goal / scope / excluded areas / output / verification

这样一个 Agent 看不到完整会话，也能知道自己应该做什么、不能做什么、交付什么，以及主会话怎样验收。

主会话仍然负责路由、合并和最终验收。委派只能移动执行段，不能移动授权。

### 长程任务开发者：让暂停成为正常状态

长任务最常见的失败不是代码写错，而是中断后无法恢复。Spec Harness 把状态保存在磁盘上：

- 已完成的任务留在 tasks.md。
- 验证命令和结果留在 checklist.md。
- 复杂并行执行的计划和 JSONL 结果留在任务包的编排资产中。
- 归档后的完成摘要随 Git 历史保存。

恢复时，先看任务包和 status，不必从聊天记录重放一遍。

## 一个核心选择：编排不依赖宿主 Workflow

Spec Harness 当前使用零宿主引擎。执行段由仓库自有的 workflow_fanout.py 驱动，Pi 或 Codex 只是可替换的 worker CLI 后端。

这条边界很重要：

- 宿主 CLI 不决定任务是否能编排。
- 没有某个宿主的原生 Workflow 工具时，契约仍然成立。
- 单个 worker 超时或失败时，结果记录为该 item 的失败，不会伪造整批成功。
- JSONL 结果和输出文件构成可审查的执行证据。
- 路由、验收、done 和 push 仍在主会话中完成。

它和厨房里的分工很像：主厨决定菜单和出菜标准，多个灶台可以并行做准备，但最后仍由主厨验收整道菜。灶台换了，标准不能换。

类比也有边界。软件任务不是固定配方，Agent 的输出需要独立测试；因此这个类比只解释“执行与验收分开”，不能替代真实的 verify。

## 从哪里开始

安装公开版本：

    git clone https://github.com/MicTx/spec-harness.git
    cd spec-harness
    git checkout v0.13.10
    bash install.sh

在支持 Skill 的 CLI 中，用 $spec 触发；Claude Code 使用对应的 /spec:goal 等命令。第一条目标可以很具体：

    为已有 API 增加审计日志导出，先检查现有权限和数据模型，
    再拆分任务，补接口测试和回滚说明。

如果你只想了解工作流，也可以直接阅读[长程任务教程](tutorial.md)。

先从小任务开始。让任务包只包含一个清楚的目标，运行一次真实验证，再逐渐增加并行评审和恢复执行。你会很快发现：好的长程开发不是让 Agent 永远不停地工作，而是让每一次停下都留下下一次可以信任的起点。

## 这套方法不替你做什么

Spec Harness 不会替你决定产品需求，不会保证生成代码没有业务错误，也不会把所有任务都拆成并行任务。简单的一次性修复不需要任务包；复杂任务才需要额外的结构。

项目当前采用非商用源码许可。你可以阅读、修改和用于非商业用途，但商业使用和销售不在许可范围内，完整条款见 [LICENSE](../LICENSE)。

## 最后的问题

当一个 Agent 说“已经完成”时，你真正想知道的不是它写了多少代码，而是：

- 它解决的是不是原来的问题？
- 它有没有越过边界？
- 验证是否真的运行过？
- 下一个人能不能从磁盘上的记录继续？

Spec Harness 把这四个问题放进一次开发工作的结构里。它不让工作变得更重，而是把原本藏在记忆、聊天和猜测里的重量，变成可以阅读和复核的文件。
