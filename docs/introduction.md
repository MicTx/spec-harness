# 我们怎样让 AI 编程真正完成一项长期工作

给一个函数名，Agent 往往能写出第一版。把任务拉长到两天、换一次会话，再加上测试、审查和 Git 收尾，难点就换了：我们还能不能说清楚它正在解决什么、哪些文件不该碰、以及“完成”凭什么成立？

Spec Harness 从这组问题出发。它不提供模型，也不替我们做产品决定。它把长期任务放进一个可以阅读、恢复和审计的工作面：

    目标 → 范围 → 任务 → 验证 → 归档 → 提交 → 推送

这条线看起来像流程，实际是一种记忆结构。每一步都留下下一位 Agent 可以消费的证据。

## 一个熟悉的失控场景

假设我们要给已有服务增加“审计日志导出”。Agent 很快找到路由、写出导出函数，也补了几条测试。真正的问题却在后面出现：导出包含哪些事件？权限沿用哪一层？能改数据库吗？测试验证了服务函数，还是用户实际走过的接口？如果下周换一个 Agent，谁知道哪些决定已经确认？

Git 记录文件，测试记录命令，聊天记录记录讨论。它们都是真的，但各自只保存一部分真相。长期工作需要一张把这些事实连起来的纸。

## 三张纸先把问题固定住

任务包通常只有三个核心文件：

    .spec/specs/YYYY-MM-DD_slug/
    ├── spec.md
    ├── tasks.md
    └── checklist.md

**`spec.md` 先回答“要解决什么”。** 它写目标用户、已确认事实、关键假设、待确认问题、范围外内容和最小实现路径。比如：本轮允许修改导出 API 和接口测试，但不重做数据库和权限模型。

**`tasks.md` 再回答“每一步怎样算完成”。** 每个任务至少有两个字段：`boundary` 说明能改什么，`verify` 说明用什么真实命令证明完成。没有前者，任务会膨胀；没有后者，勾选框只是感觉。

**`checklist.md` 最后回答“整项交付是否可信”。** 它把边界、文档、构建、回归、验收证据和必要的手工验证放在一起。单个任务完成，不等于整项工作可以交接。

这三张纸的关系很简单：第一张给方向，第二张推动动作，第三张阻止过早宣布完成。它们都是普通文本，所以人能读、Git 能审、脚本能检、新会话也能恢复。

## 为什么不用一条更长的提示词

长提示词可以提醒 Agent 做事，却不能保存它已经做过什么。任务包把判断变成可以复查的对象：

- 目标仍是原来的问题吗？看 `spec.md` 的目标和范围。
- 改动越界了吗？看每个任务的 `boundary` 和 Git diff。
- 验证真的运行过吗？看 `verify` 和验收证据，而不是看一句“通过”。
- 下一位从哪里继续？看未完成任务、失败原因和报告脚本输出。

对委派也一样。一个独立 worker 至少要收到目标、范围、排除项、输出和验证方式。主会话负责路由、合并、验收和 Git 收尾；worker 的输出不能替代验证。

## 并行是选项，不是终点

任务形状适合时，仓库自有的 `workflow_fanout.py` 可以把多个独立视角分发给可替换的 Pi/Codex worker CLI。结果写入 JSONL，超时只影响对应 item，主会话仍然拥有同一份任务合同和验收权。

这个类比只帮助我们理解“执行和验收分开”。它不能证明软件正确；正确性仍由真实测试、门禁和用户路径决定。任务无法拆出清晰边界时，串行执行更诚实。

## 从一个小目标开始

安装一个固定版本：

```bash
git clone https://github.com/MicTx/spec-harness.git /tmp/spec-harness
cd /tmp/spec-harness
git checkout v0.13.10
bash install.sh
```

然后在目标项目里使用 `$spec`，或通过 Claude Code 的 `/spec:goal` 给出一句完整目标。也可以直接运行 `scripts/init_spec_package.py` 观察任务包的三张纸。

如果今天暂停，下一位 Agent 不应该先问“我们聊到哪里了”。他应该能从任务包看到：已经知道什么、还缺什么、哪条验证失败，以及接下来最小的一步是什么。

## 留下四个问题

当 Agent 说“完成了”，重新问一遍：

1. 它解决的还是原来的问题吗？
2. 它有没有越过约定的边界？
3. 验证是否真的运行过？
4. 下一位接手的人能从哪里继续？

Spec Harness 没有把这些问题变成口号，而是变成文件、任务、命令和 Git 记录。长期 AI 编程因此获得一种朴素的能力：可以继续，可以复核，也可以交接。
