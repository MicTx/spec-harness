# 我们怎样让 AI 编程真正完成一项长期工作

AI 已经很会写代码了。

给它一个函数名，它能补出实现；给它一段报错，它能提出修复；给它一个页面，它能很快搭出第一个版本。可一旦任务从“写一个函数”变成“把一个系统改好”，事情就不再只是生成代码。

我们会遇到另一组问题：

- 需求在多轮对话后还是原来的需求吗？
- Agent 修改的范围有没有悄悄扩大？
- 测试通过的是一个孤立函数，还是用户真正走过的路径？
- 中途暂停几天后，下一位接手的人还能继续吗？
- 一句“已经完成”，究竟拿什么来证明？

Spec Harness 就是从这组问题出发的。它是一套面向 AI 编程的规范驱动工作流 Skill，帮助我们把长期任务放进一个大家都看得懂、查得清、接得上的工作面。

它不提供模型，也不代替我们做产品决定。它做的是另一件事：把目标、范围、执行、验证和 Git 收尾放进同一条证据链。

    目标 → 范围 → 任务 → 验证 → 归档 → 提交 → 推送

## 先看一个我们都熟悉的场景

假设我们要给已有服务增加“审计日志导出”。

第一轮对话往往很顺利。Agent 找到路由，写了导出函数，又补了几条测试。真正的麻烦通常在后面才出现：

“审计日志”到底包括哪些事件？导出接口能改哪些文件？权限应该沿用哪一层？测试覆盖的是导出服务，还是实际接口？如果换一个 Agent，谁知道已经确认过哪些事实？

这些问题并不一定会立刻让代码报错。它们更像是施工现场的标记没有留下：每个人都在工作，却没有一张共同的图纸。

Git 记录了文件，测试记录了命令，聊天记录记录了讨论。每一种记录都是真的，但每一种都只保存了一部分真相。长期开发需要让它们互相指向。

## 我们先把问题放到桌面上

Spec Harness 使用一个很小的任务包。它通常只有三个核心文件：

    .spec/specs/YYYY-MM-DD_slug/
    ├── spec.md
    ├── tasks.md
    └── checklist.md

你可以把它看成一张共享工作台。

### 第一张纸：我们到底要解决什么

spec.md 负责把问题说清楚。

它记录目标用户、已经确认的事实、仍然需要说明的假设、范围外的事情，以及最小实现路径。比如：

    本轮允许修改：导出 API、序列化模块和接口测试。
    本轮不修改：数据库迁移、权限模型和前端页面。

这两句话看起来很普通，却能挡住长期任务里最常见的漂移：我们本来只要增加导出，后来却顺手开始重做权限和前端。

### 第二张纸：每一步怎样算完成

tasks.md 负责把目标拆成可以执行的结果。

每个任务至少有两个字段：

- boundary：这一步可以改变什么。
- verify：我们怎样用真实命令证明它完成。

例如：

    - [ ] 增加审计导出接口
      - boundary: 只修改 API 路由、导出服务和接口测试
      - verify: 运行接口集成测试，并用临时数据核对导出内容

boundary 解决“做到哪里为止”，verify 解决“凭什么说做完”。没有 boundary，任务容易膨胀；没有 verify，复选框很容易变成一种感觉。

### 第三张纸：交付是否可信

checklist.md 负责最后的验收。

这里不只是写“测试通过”。我们还要核对文档、边界、构建、回归和必要的手工验证。任务完成，代表某一步做完；清单通过，才代表整个交付可以被别人接手。

这三个文件的分工很简单：

- spec.md 说明问题和边界。
- tasks.md 组织执行和验证。
- checklist.md 判断交付是否可信。

因为它们都是普通文本，我们可以阅读它们，Git 可以审查它们，脚本可以检查它们，新的 Agent 也可以从它们恢复上下文。

## 我们需要的不是更长的提示词，而是更短的证据链

对 AI 学习者来说，任务包把“我觉得对”变成“我能证明”。你会逐渐习惯把每个判断写成三个问题：目标理解了吗？改动越界了吗？验证真的运行了吗？

对编程者来说，任务包让分支和提交有了语义。Git 分支告诉我们哪些文件一起变化；任务包告诉我们这些变化为什么属于同一个目标；verify 证据告诉我们它们是否达到目标。

对 Agent 开发者来说，任务包给委派提供了合同。一个独立工作单元不能只收到“把这一部分做好”，它至少要收到：

    goal / scope / excluded areas / output / verification

这样，即使它看不到完整会话，也知道该做什么、不能做什么、交付什么，主会话又如何验收。

对长程任务开发者来说，任务包让暂停变得正常。完成的任务、验证命令、失败原因、并行结果和归档摘要都留在磁盘上。我们不必每次都从聊天记录重新猜测下一步。

## 并行不是目的，稳定的执行面才是

当任务可以拆成多个独立视角时，我们当然可以并行。但并行本身不能解决边界混乱和验收缺失。

Spec Harness 当前使用零宿主引擎：执行段由仓库自有的 workflow_fanout.py 驱动，Pi 或 Codex 只是可替换的 worker CLI 后端。

这意味着我们可以换宿主，仍然保留同一份契约：

- 宿主工具不会改变任务的边界。
- 单个 worker 超时，只记录为这个 item 的失败。
- JSONL 结果和完整输出文件可以被复核。
- 路由、合并、验收和 Git 收尾仍由主会话负责。

我们可以把它想成一起做饭：有人准备食材，有人处理配菜，但菜单和出菜标准必须由同一张桌子维护。这个比喻只解释“执行与验收分开”，并不能替代测试；软件结果仍然要靠真实验证。

## 从一个小目标开始

我们不需要一开始就设计一套宏大的 Agent 平台。先选一个真实但边界清楚的任务，例如：

    为已有 API 增加审计日志导出，先检查权限和数据模型，
    再拆分任务，补接口测试和回滚说明。

安装公开版本后，在支持 Skill 的 CLI 中使用 $spec；Claude Code 使用对应的 /spec:goal 入口：

    git clone https://github.com/MicTx/spec-harness.git
    cd spec-harness
    git checkout v0.13.10
    bash install.sh

然后，让工具先写清问题，再开始实现。长程开发的第一个进步，往往不是让 Agent 写得更多，而是让我们终于知道它正在解决什么。

## 和我们一起保留四个问题

当 Agent 说“完成了”，我们可以一起再问一遍：

1. 它解决的还是原来的问题吗？
2. 它有没有越过约定的边界？
3. 验证是否真的运行过？
4. 下一位接手的人能从哪里继续？

Spec Harness 没有把这些问题变成新的口号，而是把它们变成文件、任务、命令和 Git 记录。这样，AI 编程就不再只是一次对话里的灵感，而更像一项可以共同推进、共同检查、共同交接的工程工作。
