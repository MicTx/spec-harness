# 术语表

本书术语约定；不主张这是行业唯一的 Harness 定义。

| 术语 | 含义 |
| --- | --- |
| Agent | 能调用工具、读写文件、执行命令的智能体，不是只聊天的模型窗口 |

| 单线闭环 | 一个人、一个任务包、一条 integration branch 走完规划到收尾 |

# 前言：为什么 Agent 需要 Harness

## 场景：你经历过的那种夜晚

十一点，你对着终端里的智能体说：「帮我把存储迁到对象存储。」它利落地列了计划，然后开始改代码。头两个小时一切顺利，你甚至有点感动。第三个小时，它顺手「优化」了一个跟迁移毫无关系的模块；你让它改回来，它道歉，改回了大部分。第四个小时，上下文窗口到了尽头，你开了一个新会话，把之前的对话摘要贴过去——它读完，自信地继续，然后把你两个小时前已经改对的文件又改了一遍。凌晨两点你按下 Ctrl-C，面对工作区里四十多个被改动的文件、一半跑通的迁移脚本和三片说不清状态的测试，你意识到一件事：**没有人，包括你自己，能说清这次工作现在处于什么状态。**

第二天你在社交平台上写：「模型还是不够聪明。」点赞的人很多。但你心里知道不完全是这样。模型其实相当聪明——每一次单步操作它都做得像模像样。出问题的是别的东西：目标只存在于对话里，对话会消失；完成从来没有定义过，所以永远无法被证明；改动没有边界，所以什么都会被牵连进去。

这类事故不一定能靠更强模型消除，其中很大一部分是**结构问题**。模型能力仍然重要，但结构上的缺口需要结构性的补足。

## 原则：三个立论

这本书的全部内容建立在一组判断上，先把它们摆在明处，你合不合意，一眼可断：

**一、先检查结构，再判断模型能力。**更强的模型可能减少错误，但不能保证持久状态、授权边界和验收机制自动成立。意图没有载体、上下文会清零、完成没有判据、改动没有边界——这四个洞是过程结构上的，堵洞要用结构。

**二、文件是真源，对话不是。**凡是重要的——范围、决定、进度、验收标准——必须落到比会话更持久的载体上，而且必须落到机器可解析的形态。会话用来干活，不用来记事。谁说了算？磁盘说了算。

**三、完成必须可证明。**「完成」不是一种感觉，是一个可验证的断言：跑了什么命令、得到什么退出码、留下什么证据。不可证明的完成，一律按未完成处理。

本书把由这三个立论构建的工程约束层称为 **Harness 的控制平面**。行业中的 Harness 含义更宽，还可能包含工具执行、上下文管理、预算与权限等运行时能力；本书聚焦其中可恢复、可验证的工程工作流，不把它当作唯一或完整定义。一个比喻：智能体是一台马力惊人的发动机，Harness 是围绕它的车架、方向盘、仪表盘和刹车。没有车架的发动机当然也能转，喷着火苗，非常壮观，但你没办法开着它去任何地方。发动机越强，车架越重要——这不是悖论，而是这本书全书的立论。

读完这本书，你将能够：

- 用一条清晰的因果链解释自己的项目为什么会返工，而不是归咎于「模型变笨了」；
- 在自己的仓库里，用 Markdown、Python 标准库和 Git，从零理解并运行一个仅用标准库的最小工作流 Harness；
- 为一次跨会话的复杂工作建立「范围、任务、验收」三件套，让新会话根据文件与现场证据接上进度；
- 用机器门禁代替「看起来完成了」，用退出码和证据关闭任务，而不是用印象；
- 把一次复杂改动安全地落进 Git——干净的工作树、独立的分支、提交与发布分离；
- 判断什么时候值得请临时助手并行干活，什么时候该由主线程一个人接管。

## 反模式：这本书不做什么

为了让「是什么」更清晰，先把「不是什么」划出来。以下四种期待请提前收回：

- **不是提示词大全。**提示词影响一次调用，Harness 约束整个过程。两者不冲突，但这本书只讲后者。如果你在找「一句话让模型听话」的咒语，这本书会令你失望。
- **不是模型评测。**不会告诉你哪家模型更强，也不讨论采样参数。执行平面可替换是本书原则，为它写排行榜没有意义。
- **不是某个 CLI 的操作手册。**书里会出现命令，但命令是证据，不是主角。原则写在正文，命令细节收在附录。换一个工具，原则原样成立。
- **不是多智能体炫技。**并行助手只在边界干净、值得拆分时出场，而且我们会专门花一节讲什么时候**不**该拆。先用单线闭环把失控治住，再谈编队。

## 贯穿案例：这本书自己

技术书最尴尬的局面，是书里讲的方法连作者自己都不用。这本书不打算这样。

本书从立项、拆任务、写章节到导出电子书，使用书中讲的工作流管理：它有自己的任务包（范围、任务、验收三件套），有自己的校验脚本——每个章节必须包含「场景、原则、最小实现、反模式、练习」五个环节、正文字数必须落在设定区间、电子书必须能由脚本真实构建出来，任何一项不满足，整个项目的验收检查就退出非零。你会在各章看到这个任务包的真实片段：范围怎么冻结、任务怎么拆、门禁怎么拦住不合格的章节、无关改动怎么被挡在提交之外。

写书是一次真实的适用性实验，不是对任意重构的保证。数据迁移、并发执行与敏感权限仍需要各自的工程设计。

同时，伴随教学程序只用 Python 标准库，测试在隔离临时目录运行；Git 与 EPUB 构建另有工具依赖。正文中的配置片段用于说明协议，不等于已实现照片业务。教学版与参考实现共享原则，但不共享完整能力或文件格式。

## 假设的读者

你应该已经满足这三条：

1. 会用至少一个支持工具调用的编程智能体（能读写文件、执行命令的那类，而不只是聊天窗口）；

- 第 5 章串单线闭环：从一句话目标到可恢复执行，中断之后接得上。
- 第 6 章上机器门禁：用退出码和证据关闭任务，不再相信「看起来完成」。
- 第 7 章做 Git 收尾：干净工作树、独立分支、提交与发布分离。

每章固定五个环节：**场景**（一个具体的项目事故）、**原则**（这一部件的设计逻辑）、**最小实现**（你可以照抄的代码与约定）、**反模式**（命了名的常见错误）、**练习**（在你自己的仓库上动手）。如果你是精读型读者，建议每章的练习当章做完——这套东西的手感只能在键盘上长出来。

一个阅读提醒：正文里反复出现一个词——**真源**（single source of truth）。每当看到它，问一句「此刻谁说了算」：是对话说了算、记忆说了算，还是磁盘上的文件和脚本的退出码说了算。这个问题是全书的暗线。

## 最小实现：开工前的准备

读这本书是动手课，不是听讲课。开工前把环境备齐，后面每章的「最小实现」才能当章落地。陈默、拾光相册以及涉及用户数量、时间、事故的情节均为教学虚构，不是用户调研、实测或商业背书：

- **Python 3.9 或更高版本。**伴随教学 Harness 使用标准库，无需第三方 Python 包；构建电子书另需 Pandoc。用 `python3 --version` 确认。
- **Git。**第 7 章之前的练习也需要你随时能开分支、看 diff。
- **一个支持工具调用的编程智能体。**任何能读写文件、执行命令的 CLI 都行——这是执行平面，具体哪家不影响正文。
- **一个真实的练习仓库。**最好是你在维护的真项目，哪怕是私人小项目；不必专门造一个玩具仓。书中所有练习都指向你自己的仓库，真实仓库给的反馈，玩具仓给不了。

准备一个空目录也行：附录 B 给出 Harness 的完整目录地图，第 8 章有一晚上的最小接入清单。工具就绪后翻页——我们从陈默的一个糟糕周末开始。

# 第 1 章 智能体为什么会失控

要建 Harness，先得承认一个不舒服的事实：不少「AI 编程事故」与我们给模型的工作环境有关，不能只从模型能力解释。本章先解剖一次典型的失控，把它拆成四个结构性缺口；往后整本书，就是在逐个堵上这四个缺口。

## 场景：陈默的周末

陈默是独立开发者，一个人维护着一个叫「拾光相册」的照片托管服务：两千多个付费用户，Flask 单体，Postgres，照片直接躺在服务器的磁盘上。这套存储是他一年前搭的，现在磁盘报警频繁，他决定把照片迁到 S3 兼容的对象存储，顺便把缩略图生成改成异步。

这是个两三天的活，他决定交给智能体，自己当监工。周五晚上十点，他在项目根目录敲下：

```
$ agent "把拾光相册的照片存储从本地磁盘迁移到 S3 兼容对象存储，
        缩略图改成异步生成，保持现有接口不变。"
```

开局很顺。智能体先读了代码，列了一个像模像样的计划：改存储层抽象、写迁移脚本、加 Celery 任务、补测试。陈默扫了一眼，觉得靠谱，回了个「继续」。

前两个小时，它稳扎稳打地改完了存储层。第三个小时出了第一次偏航：它觉得 `photo.py` 里的缓存逻辑「和存储相关」，顺手重构成了一个新的装饰器语法。陈默盯着 diff 觉得不对，说「这部分不要动」。它道歉，回滚——回了大概百分之九十，剩下的百分之十藏在另一个文件里，陈默没看见。

第四个小时，真正的转折来了。会话上下文逼近窗口尽头，智能体开始「忘记」两小时前的决定：它把已经改对的上传接口又按旧思路改了一遍，测试红了。陈默让它看测试，它修；修好了另一个，又红了。它像一条咬住自己尾巴的蛇，每次修复都在制造下一轮问题。

凌晨一点，陈默做了大多数人在这个时刻都会做的事：新开一个会话，把旧对话的摘要贴进去。新会话的智能体很有礼貌，声称完全理解了上下文，然后问了三个陈默一小时前刚回答过的问题，接着按自己的理解「重新梳理」了方案——和旧会话已经做了一半的方案并不一致。

凌晨两点半，陈默按下 Ctrl-C。工作区的状态是：四十七个文件有改动，其中至少五个与迁移无关；迁移脚本跑了一半，第一批照片已经上传到桶里，但数据库里的记录没有更新；测试套件十二红；没有人——包括陈默自己——能一口说清「现在到底进行到哪了」。

在这个教学故事中，他花了后续两个周末善后，复盘时说：「我不是在用 AI 编程，我是在替 AI 打扫战场。」

## 失控的因果链

把陈默的周末拆开看，模型在每一个单步上的表现其实都不差：读代码准确，计划合理，单文件修改质量在线。灾难是**步骤之间**长出来的。精确地说，有四个结构性缺口，每一个都对应你能在自己项目里复现的一类事故。

### 缺口一：目标只存在于对话里

陈默的完整意图——「迁移到 S3、缩略图异步、接口不变、别的都别动」——从来没有落在一个持久的载体上。它活在对话的滚动条里，随上下文一起被截断、被摘要、被新会话的转述稀释。对话是**易失的线性流**：它适合交换信息，不适合承载规格。

后果是范围漂移：智能体对「范围内」的理解随对话演进，而且只能随对话演进。你说过的话会被窗口挤出去，你没说的话它就会自己脑补。缓存重构那百分之十的残留，本质上是「别的都别动」这条约束没有实体，只能靠模型在每一步重新想起。

### 缺口二：上下文窗口是易失的

第二个缺口是第一个的放大器。人类工程师做两周的活，靠的是外化记忆：任务看板、设计文档、代码注释、测试。智能体在裸会话里做同样的活，只有一块会定期清零的黑板。于是它不是「笨」，而是**失忆**：它不知道自己上个会话做过什么决定，只能从残缺的摘要里重建一个自信的近似。

陈默新开会话那一刻，项目状态事实上出现了两个真源：磁盘上的半成品代码，和新会话脑子里基于摘要的方案。两者不一致时，执行平面听谁的？听后到的那个。这就是「越改越偏」的机制——不是偏心，是没有锚。

### 缺口三：「完成」从来没有定义过

「把存储迁到 S3」——做到什么程度算完？迁移脚本跑通算完，还是全量数据校验过算完？测试全绿算完，还是生产灰度一周算完？陈默从没定义，智能体自然按自己的标准宣布完工。而它的标准是「我把我打算做的都做了」。

这是「做完无法验收」的根源：**没有验收标准的任务，只有宣布，没有完成。**更麻烦的是反向情形——任务其实做完了，但陈默不敢确定，于是反复让智能体「再检查一下」，又制造出新一轮不必要的改动。验收标准缺失同时生产两类事故：假阳性（说完成其实没完成）和假阴性（完成了却不敢信）。

### 缺口四：改动没有边界

第四十七个文件里，混着缓存重构、日志格式调整和一个陈默始终没弄明白为什么会存在的 `utils.py` 大改。因为从智能体的视角，整个工作区是它的作业面——没有任何机制告诉它「这些文件属于这次任务，那些不属于」。

没有边界，就没有「无关改动」这个概念——一切改动都是「顺手优化」。而无关改动是验收的天敌：你要么花同样的精力把它们全部审查掉，要么放任它们混进发布。陈默善后两周里的大半时间，花在回答「这个改动是谁、为什么、要不要留」上。

### 因果链合龙

四个缺口连起来，就是那条你熟悉的事故因果链：

```
意图没有外部载体（缺口一）
    → 上下文一断，意图失真（缺口二）
    → 没有完成定义，进度不可判定（缺口三）
    → 没有改动边界，污染全面扩散（缺口四）
    → 没有人能说出「现在在哪」
    → 返工、善后、不信任，循环加深
```

这条链描述结构性缺口，不否认模型能力、提示词质量和工具实现本身也会导致错误。更好的模型与提示词可能改善行为，但不能单独提供持久状态、幂等执行与强制权限，这些仍需**过程结构**补足。

## 原则

从因果链可以推出本章的三条原则，它们也是全书的地基：

**原则一：失控是结构问题，先修结构再换模型。**遇到返工，第一反应不该是「换个更强的模型」或「写个更凶的提示词」，而是问：这次返工经过因果链上的哪个缺口？结构性缺口要用结构堵，本书后续每一章都在做这件事。

**原则二：对话不是真源。**凡是重要的——意图、范围、决定、进度、验收标准——必须外部化到比会话更持久的载体上：文件。会话是用来干活的，不是用来记事的。谁说了算？磁盘说了算。

**原则三：完成必须可证明。**「完成」不是一种感觉，是一个可验证的断言：跑了什么命令、得到什么输出、留下什么证据。不可证明的完成，一律按未完成处理。

这三条原则彼此咬合：外部化让意图在会话切换后存活，可证明让完成有了判据，两者合起来，失控的链条就从中间断开。

## 最小实现：一份失控解剖报告

Harness 的第一块砖小得出奇：一张四行的 Markdown 表。在你最近一次失控的项目里（每个人的版本库里都埋着一具），建一个 `autopsy.md`，回答四个问题，每个问题对应一个缺口：

```markdown
# 失控解剖：项目名与日期

| 缺口 | 当时的实际情况 | 如果重来，我会把这一条写在哪里 |
| --- | --- | --- |
| 意图载体 | 只在对话里说过，后来被截断 | spec 文件：范围与非目标 |
| 上下文断裂 | 换会话后重做了两小时的工作 | 任务文件：每步的完成判据 |
| 完成定义 | 从未定义，靠感觉宣布 | 验收清单：逐条可执行的检查 |
| 改动边界 | 智能体自由发挥到第 47 个文件 | 任务边界：允许改动的路径清单 |
```

写的时候有个诀窍：第三列只准写「写在哪里」，不准写「我会更小心」。**「更小心」是性格，「写在哪里」是结构。**Harness 工程不改善性格，只建结构。

在这个教学情节中，陈默用这张表复盘过去的返工，发现多次指向同一行：意图只存在于对话里。这个发现让他把关注点从「怎么调教智能体」彻底转向了「怎么搭结构」——也就是从第 2 章开始的事。

这张表还顺便定义了这本书后面所有章节的分工，你可以先扫一眼这个映射，读完全书再回来核对：

| 解剖报告的第三列 | 对应章节 | 落地产物 |
| --- | --- | --- |
| spec 文件：范围与非目标 | 第 3 章 | 假设与边界的范围文档 |
| 任务文件：每步的完成判据 | 第 4 章 | 任务包三件套 |
| 验收清单：可执行检查 | 第 6 章 | 机器门禁脚本 |
| 任务边界：允许改动的路径 | 第 4、7 章 | boundary 约定与 Git 纪律 |
| 中断后接上 | 第 5 章 | 单线闭环与路由 |

## 反模式

四种开局姿势对应四个缺口，每一种都值得命名，因为你在代码评审和社区帖子里会反复认出它们：

**全能开局。**「帮我把这个项目重构一下。」不给范围、不给非目标、不给验收标准，把整个仓库当成作业面。这是缺口一和缺口四的复合体，也是所有反模式里最致命的一个。解药在第 3 章：显式假设与最小实现。

**无限续杯。**在一个会话里无限追加任务，直到上下文溢出，然后靠摘要续命。摘要是有损压缩，每一轮续杯都在降低意图的保真度。解药在第 4、5 章：把长活拆成跨会话的任务包，让每个新会话从文件而不是摘要开始。

**记忆验收。**「我看过 diff 了，应该没问题。」用印象代替证据。记忆验收的问题不是懒，是**不可复核**——三个月后没人能重放你的「看过」。解药在第 6 章：退出码与证据。

**混树开发。**工作区里永远躺着七八件没提交的半成品，任何新任务都从脏树开始，最后所有改动搅成一锅。解药在第 7 章：干净工作树与提交纪律。

值得说明的是，这些反模式在纯人类时代就已存在——混树开发在 Git 教科书里被骂了十五年。智能体只是把它们的发作频率和爆炸半径放大了一个数量级，因为它的「手速」远超人类，而自省远逊于人类。

## 练习

所有练习都在你自己的仓库里做，这本书不提供标准答案，只提供验收判据。

1. **做你自己的解剖。**挑最近一次真实的失控（返工超过半天的都算），填 `autopsy.md` 的四行表。验收：第三列每格都是「写在哪里」式的结构答案，没有一格是「更小心」。
2. **找到你的第 47 号文件。**用 `git log --stat` 回看那次失控的提交（如果它有幸被提交的话），数一数改动文件里有多少与原始目标无关。验收：能说出每个无关改动的「出生原因」属于哪个缺口。
3. **翻译一次抱怨。**把你或同事最近一条对智能体的抱怨（「它又开始自作主张了」之类）翻译成因果链上的某一环。验收：抱怨里出现的行为，能精确对应到缺口一到四中的某一个，而不是笼统的「它不行」。
4. **预演一次中断。**现在就在你当前的项目里，向智能体布置一个十分钟的小任务，中途强制新开会话，只靠摘要继续。观察意图失真发生在哪一步。验收：能指出新会话重建方案时偏离原意的具体位置。

第 2 章开始动工。我们先画出 Harness 的整体结构图——四层各管什么、为什么聊天记录不能当真源——然后写下你的第一份范围文档。

# 第 3 章 四条原则：显式假设、最小实现、边界清晰、验证优先

## 场景：一份正确却没有用的范围文档

陈默写下了第一版范围：「改善照片存储的可靠性，提升性能，保持良好的用户体验。」这句话没有错误，也几乎没有约束力。采用对象存储可以符合它，重写整个后端也可以符合它；增加缓存可以符合它，替换数据库同样可以符合它。一个目标如果能为互相冲突的十种方案辩护，就还没有成为可执行的规格。

他把文档发给智能体，得到了一份雄心勃勃的规划：多区域部署、分层缓存、图片去重、缩略图服务独立化。每一项都能解释为什么有价值，但加起来已不是原来那件两三天的工作。问题并非智能体恶意扩张，而是目标函数过于宽泛：当「更可靠、更快、更好」是全部约束，任何增加复杂度的方案都能自证合理。

把文档写实，不是把所有设计细节提前规定死。你需要给推理留空间，同时把不可随意改变的东西说清。本章的四条原则就是为这件事服务：显式假设让认知可审查，最小实现限定投入，边界清晰限定改动，验证优先限定完成含义。

## 原则：四个问题，四种约束

### 显式假设：把确定、推定和待决分开

事实是已经获得支持的陈述，例如代码当前用磁盘路径保存照片。假设是为了推进工作而暂时采用的前提，例如现有照片总量在一个夜间窗口内可以完成迁移。待决项则是不能合理代替负责人决定的选择，例如是否允许某些付费用户经历短暂停写。

三者最大的区别不是措辞，而是变化时如何处理。事实被推翻，需要修正调查结果；假设被推翻，需要触发预先约定的重规划；待决项没有答案时，某些任务不得启动。若混在一段散文里，智能体很容易把一个暂时估计当永久授权。

| 类别 | 陈默的表述 | 如何验证或处理 |
| --- | --- | --- |
| 事实 | 当前上传接口返回本地照片标识 | 查看路由与接口测试 |
| 假设 | 一次批次可以迁移五百个对象 | 在练习数据上测量耗时与失败率 |
| 待决 | 是否允许迁移期间删除源照片 | 本轮默认禁止删除，不替用户授权 |
| 非目标 | 不重构缓存模块 | diff 中检查相关路径无新增改动 |

显式并不意味着把问题全抛给用户。工具库、目录命名、日志格式等可合理选择的细节，给出默认值与理由即可。只有答案会改变整个项目形态、无法合理假定或需要外部权限时，才应该停下来问一个聚焦问题。无限提问也是一种失控：工作看似谨慎，却没有产出。

假设还应附带失效信号。例如「若试迁移显示单批耗时超过窗口预算，先减小批次并重新估算，不自动转向分布式调度」。这样写，执行者知道什么时候继续、什么时候调整、什么时候必须重新决定。一个假设没有失效条件，就容易变成无人察觉的永久事实。

### 最小实现：减少独立变化，不减少正确性

最小实现经常被误解为「先不处理失败」。对照片迁移而言，这是最危险的节省方式。幂等、对账和保留源数据不是豪华功能，而是让迁移能够恢复的最低条件。真正可以省的是尚未需要的多区域调度、插件系统与独立缩略图微服务。

判断一个部件是不是最小范围，可以问：去掉它，核心承诺是否仍成立？去掉多区域部署，仍能把本地存储迁移到对象存储；去掉对象校验，可能把损坏的数据标成成功，核心承诺就不成立。最小方案应缩减可变性，而不是缩减责任。

另一个实用办法是写「暂不引入」清单。这不是永久否决，而是在本次目标下限制新增机制。先让一个对象正确上传、查询与回退，再批量处理；先让一个真实工作流可恢复，再考虑多 Agent 协作。每增加一个独立服务，就增加一组需要解释的状态、部署和失败方式。

对本书而言，最小交付是可读源稿、电子书构建与能复现的教学程序。不需要同时建立在线学习平台、付费墙或视频课程。电子书是否畅销还依赖定位、渠道、价格与真实读者反馈，不能用文件数量或字数指标替代市场结果。

### 边界清晰：分别说明可以读什么、可以改什么

任务的 boundary 首先是改动边界。让存储适配器任务修改 `app/storage.py` 和对应测试，并不意味着它有权修改全部配置。若执行过程中发现必须调整一个共享接口，应提出具体变更理由，由主线程批准或重新拆任务，而不是把「相关」当成无限扩大权限的词。

读取边界与写入边界也不同。助手可能需要读接口声明、术语表和验证脚本才能工作，但它不需要改这些共享文件。在并行写书中，目录与术语表是输入，章节文件是输出；把两者都写成「属于你」，就会引发多方同时改变约定。

边界还有强弱之分。Markdown 中的限制属于协作协议；受信任的执行者应遵守，但普通文件本身不会阻止越权系统调用。需要强制隔离时，要通过工作区、进程账户、容器、文件权限或工具网关限制实际能力。不要把一句「禁止访问」描述成已经实施的操作系统防线。

路径边界不能替代语义边界。一个任务只允许修改两份文件，仍可能在这两份文件里重写整个产品逻辑。因此审查既要看文件名，也要看差异内容是否服务目标。自动路径检查帮你缩小审查面，不帮你做完全部审查。

### 验证优先：先说明看到什么才相信

写 verify 不是让人未写代码先猜实现，而是提前确定可观察结果。比如「上传同一照片两次，得到稳定对象标识，数据库不产生重复记录；模拟对象存储失败，接口返回受控错误且源数据仍在」。这些都是行为，不绑定某个内部类名。

一个好的验证合同还包括反例。只看成功上传，不能证明重试正确；只看 EPUB 文件存在，不能证明内部章节顺序正确；只看任务复选框全勾，不能证明证据属于当前版本。负向样本告诉你门禁是否真的会拒绝不合格输入。

验证优先也不意味着所有判断都自动化。文字是否易读、场景是否可信、设计是否对准用户需求，都可能需要人工审查。关键是让人工审查有明确对象与结论，不要一句「看过了」涵盖全书。机器检查结构，测试检查行为，编辑检查内容，各自报告自己的边界。

## 最小实现：把宽泛目标改成可执行范围

把陈默原来的三句愿望，改写为下面这份范围。它仍没有规定每一个函数怎么写，但已经足以排除大部分无关方案。

```markdown
# 照片迁移范围

Status: active

## Goal
已有上传接口改用 S3 兼容对象存储，保持响应字段不变。
提供可重跑的迁移工具；迁移成功须通过对象与记录对账。

## Facts
当前上传接口、路径规则和接口测试已经查明。

## Assumptions
先在隔离的练习数据集验证，再决定真实数据批次。
若批次超时或发现对象不一致，停止扩大批次。

## Non-goals
不重构缓存，不更换数据库，不删除源照片。
不在本轮引入多区域部署或独立图片服务。

## Acceptance
上传接口兼容测试通过。
重复迁移不产生额外记录。
故障时保留源数据并输出可查询的失败项。
最终 diff 可追溯到当前任务。
```

这里的英语状态字段服务教学解析器，中文正文服务读者。二者各有所长：机器解析少量固定结构，人和智能体理解剩余语义。不要为了机器方便，把整个需求变成难读的配置语言；也不要为了自由排版，让状态字段出现五种拼法。

下一步不是直接把这篇文档交给执行者就不管，而是做一次反向推演。假设智能体要重构缓存，能否从范围中找到授权？不能。假设它提出保留源照片以便失败恢复，是不是范围外扩张？不是，那是核心正确性要求。假设它认为需要一个新服务，是否有权自行部署？没有，应解释为什么最小方案不足。

这种推演可在五分钟内完成，比写一页「务必遵守以上要求」更有用，因为它检验的是约束有没有区分能力。没有区分能力的规格，看起来详尽，执行时仍然任人解释。

### 用本书做一次目标拆解

「写一本畅销电子书」混合了可控制的产物目标与不可直接控制的市场结果。合理的工程转换不是承诺销量，而是把当前可验收的承诺列出来：面向有编程经验的读者、用一个持续案例解释 Harness、提供真实可运行的教学程序、每章有练习、源稿可构建为 EPUB、明确技术适用边界。

字数区间是一种防止交付过薄或无节制扩张的辅助约束，不是文学或商业质量评分。若为了达到下限重复段落，即使计数器通过，产品审查仍应失败。若章节很短但讲得完整，也应该在明确修改范围后决定是否接受，而不是悄悄降低阈值迁就当前稿件。

同样，自动化只能检查已定义的东西。书中的人物必须标明为教学虚构；技术例子不能声称拥有未实现的安全隔离；未运行的代码不能写成已验证。把这些内容写入审查合同，才是对「可售技术书」的负责方式。

### 审查一次变更请求

陈默在实现中发现原来所有照片路径都拼在一个公共函数里，迁移必须改这个函数。此时应该提交一个小而完整的变更说明：现有边界为什么不足，拟增加哪个文件，哪些任务会受到影响，如何验证旧调用方没有退化。主线程批准后更新范围和任务，再实施。

不要把变更审批理解成写作业等盖章。小项目里主线程可以当场判断并记录；复杂项目里则可能需要负责人授权。共同点是决定先于执行，而且决定能在换会话后被找到。没有记录的口头许可，到了下一次恢复又会变成两个版本的记忆。

## 反模式：四条原则也会被滥用

**假设墙。**罗列几十条假设，既没有证据也没有失效条件。结果不是更透明，而是没人知道哪三条决定系统成败。优先写会改变范围、正确性或成本的假设，其他日常细节不必上升为正式风险。

**最小借口。**把错误处理、数据校验、资源回收都推到「下一版」，却把非必要界面和插件系统塞进第一版。最小方案首先要成立，然后才谈规模。一个会丢照片的最小迁移器，不是最小可行，是最小不可用。

**边界魔法。**认为写了允许路径就获得了强制安全保证，或者因为路径在允许列表就不再审查语义。边界同时需要协作约定、实现限制与最终核对，三者没有任何一个能独立完成全部职责。

**验证表演。**验收里写「测试通过、代码优雅、用户满意」，没有具体命令或判据。这类文字只能宣布态度，不能区分成功与失败。改成能被第三方重复观察的结果，才有工程价值。

## 练习：让四条原则互相检查

挑一个真实需求，先写一页范围，再对它做四轮检查。第一轮，把每条未证实陈述标成假设并写失效信号。第二轮，删去不影响核心承诺的机制。第三轮，列出写边界和必需读取输入。第四轮，为每个完成承诺写一个成功样本和一个失败样本。

参考判据是：一个新会话能够明确回答本次不做什么；一个实现者能在不被规定全部内部设计的前提下动工；一个审核者能指出哪条观察会让他拒绝验收。如果这三个角色仍要依赖你在旁边不断解释，文档还需要收紧。

最后故意提出一个范围扩张，例如把图片去重加入迁移任务。写下接受和拒绝各自的理由。正确答案不是永远拒绝新需求，而是能够说明它是否属于同一个目标、会改变哪些依赖、需要增加什么验证。四条原则约束的是决定的清晰度，不是把项目冻结成一块石头。

# 第 4 章 任务包：范围、任务、验收的同一真源

## 场景：知道要去哪，却不知道走到哪

范围文档写实之后，陈默的智能体不再主动重构缓存。但两天后他恢复工作，仍然遇到一个熟悉的问题：存储适配器好像写完了，迁移工具好像也跑过了，究竟下一步应该做什么？范围描述的是目的地，不是行程记录。它回答不了每一步是否完成、谁依赖谁、完成依据在哪里。

于是他加了一张待办表：写适配器、写迁移工具、补测试、上线。这张表比没有好，却还有三个洞。第一，任务太大，任何一项都可以掩盖很多未完成行为。第二，没有依赖，智能体可能在接口未确定时先写迁移工具。第三，没有证据，勾选意味着「某个时刻有人认为做完了」，新会话无法复核。

解决办法不是把任务表写得更漂亮，而是建立一份完整的任务包：范围、任务、验收各管一类事实，并通过稳定标识、依赖和证据关联。三份文件不是三次重复汇报，而是三个不同问题的答案。

## 原则：分开事实，连接责任

### spec.md 定义目标与取舍

范围文件持有问题定义、已知事实、关键假设、范围内外和成功标准。它变化得相对慢，只在对需求或方案边界作出真实决定时更新。不要把每条工具输出都贴进范围文档，否则执行者会在噪声里找不到仍然有效的约束。

范围也不应跟着测试失败随意后退。假设接口兼容是核心承诺，测试发现响应字段变化，正确动作是修实现，或者经授权改变承诺并说明影响；不能删掉「保持接口不变」这句话来让当前结果自动合理。

### tasks.md 定义执行状态

任务文件持有可执行单元及其依赖，每个单元应有稳定 id、明确边界、验证办法和完成证据。稳定标识的价值不在美观，而在防止重排造成身份变化。任务从第三行挪到第七行，仍然应是同一任务；其他任务的依赖不应该因此指向另一个对象。

任务大小应由独立验收能力决定，而不是机械规定每项两小时。能单独说明输入、输出、边界和验证，就有机会成为一个任务；必须依赖三个未定接口才能开始，则可能需要先拆出设计或调查任务。任务越小越好也不成立，过碎会让每次写文件都变成协调活动。

### checklist.md 定义最后一道判断

验收清单不是把任务再抄一遍。任务说「实现存储适配器」，验收说「用户上传行为兼容，错误路径不会丢失原照片」。前者对应实现责任，后者对应需求与质量责任。两者完全一样时，常见结果是所有任务勾完了，却没人检查端到端用户路径。

验收清单还应覆盖边界、环境和交付。例如没有混入无关改动、在干净目录能复现测试、文档说明了未支持的平台。适用外也应给理由，而不是删掉所有不容易完成的检查。这里记录的是判断，不是装饰性的复选框。

## 最小实现：让三件套形成一个状态整体

### 创建教学包

在练习仓库设置好指向本书目录的 `BOOK` 环境变量，然后执行：

```bash
python3 "$BOOK/examples/mini_harness.py" init photo-migration
```

程序在 `.mini-harness/photo-migration/` 下创建三件套，状态是 draft。已有目录会被拒绝，不会因为第二次执行覆盖你写过的需求。这个选择体现了一条朴素的数据原则：创建与恢复应是两种不同操作，恢复不能假装成重新初始化。

教学版不使用参考实现 `.spec` 的完整格式。目录名不同，就是为了让读者看见两者的兼容边界。你可以在其中实验概念，但不要把教学包丢进参考实现然后要求它识别所有字段。

把任务文件改成以下形式：

```markdown
# 照片迁移任务

- [ ] 实现对象存储适配器
  - id: adapter
  - boundary: app/storage.py, tests/test_storage.py
  - verify: python3 -m unittest discover -s tests

- [ ] 实现可重跑迁移工具
  - id: migration
  - depends-on: adapter
  - boundary: tools/migrate_photos.py, tests/test_migration.py
  - verify: python3 -m unittest discover -s tests

- [ ] 验证接口兼容与失败恢复
  - id: integration
  - depends-on: adapter, migration
  - boundary: tests/test_upload_flow.py
  - verify: python3 -m unittest discover -s tests
```

这些是计划记录，不是已经存在的业务实现。练习者需要在自己的项目完成对应模块。伴随程序不会把 verify 字段当代码执行，它只展示操作者应审查的验证办法。真正执行命令时，由操作者明确批准参数数组。

### 依赖图如何决定就绪任务

上例对应一个小图：adapter 在起点，migration 依赖它，integration 依赖前两者。某个任务就绪，需要它自己未完成，且所有显式依赖都已完成。图中的「完成」还要求存在证据，不是只看勾选符号。

没有声明依赖，不意味着工具可以从自然语言中猜出依赖。机器可以发现缺失 id、重复 id、循环关系和违反依赖顺序的勾选，却无法可靠猜测「先把环境弄好」到底是执行要求还是一句背景说明。重要关系必须写成结构。

教学实现采用迭代式拓扑验证。先收集没有未解析依赖的任务，加入已解析集合；再重复这一过程。如果还有任务未解析，却找不到任何可以推进的节点，就存在循环。缺失依赖在此之前单独报错，避免把「引用了不存在的任务」误报成循环。

这段逻辑值得读一次源代码的 `parse_tasks`。它还拒绝未知任务字段，目的是让拼错的 `depends-on` 不能被安静忽略。教学格式严格、能力较少，读者能完整理解它；生产实现可能更灵活，但灵活必须带明确的错误处理。

### 完成一个任务时写什么

任务完成后，先运行规定的验证，核对实际输出，再把任务改为勾选并补证据：

```markdown
- [x] 实现对象存储适配器
  - id: adapter
  - boundary: app/storage.py, tests/test_storage.py
  - verify: python3 -m unittest discover -s tests
  - evidence: 本次练习的适配器测试实际通过；完整输出保存于测试记录
```

上例说明字段形态，实际使用时应写入自己的命令、结果与记录位置，不能复制示例文字冒充运行证据。证据要能支持审核者的判断：它属于哪个环境、哪一版输入、测试是否包含失败路径。只写「很好」没有用；写一千行未经筛选的日志也不一定更有用。

若任务验证失败，任务保持未勾，错误成为下一步可执行工作。不要为了看板好看先勾上，再在聊天里补一句「还有小问题」。这种分裂状态在当前会话里勉强能记住，换会话就会被误认成完成。

### 验收清单的形态

```markdown
# 照片迁移验收

- [ ] 上传响应兼容，重复迁移不重复创建记录
- [ ] 对象存储失败时保留源数据，能查询失败项
- [ ] 本次差异没有缓存重构或无关配置变化
- [ ] 在隔离练习环境重跑关键路径

Acceptance: pending
```

只有实际检查完成后才勾选，并把 Acceptance 改成 passed，补上 `Evidence:` 行。教学解析器会拒绝验收通过但任务未完成的组合。它不能判断任意人写入的证据是否真实，因此最终仍需读取真实输出与改动。结构一致性是最低线，不是完整真实性证明。

## 本书的拆分：先稳定接口，再并行内容

这本书的任务图有一个共享起点：冻结目录、术语和校验规则。前言与第 1–2 章、第 3–5 章、第 6–8 章可以在该起点之后独立撰写。附录与示例也能独立推进，但示例接口必须先公布，否则不同章节会发明互不兼容的命令。

组装 EPUB 则依赖所有章节到齐。不能因为封面、目录和文件名都存在，就把构建任务提前判为完成。每章存在只是输入条件，正文完整、技术一致和电子书构建成功才是后续判据。

这张图揭示了一个常见误区：并行不是把所有事情同时启动，而是找到共享决定已经稳定的部分。若目录尚未冻结，三位作者同时写稿很可能得到三本不同的书。先用一点串行时间确定共同接口，往往比事后统一几万字更便宜。

实际尝试中，写作助手没有在看门狗要求的窗口内产生新的检查点，最终转为主线程接管。这说明任务图允许并行，不等于当前宿主一定能有效完成并行。任务包应记录真实交付，而不是按照最初计划假定所有并行都已发生。

## 任务变更与状态恢复

任务被拆分时，原有 id 怎么办？如果原任务已经有部分交付，可以保留它并明确剩余子任务，也可以在受控变更中迁移依赖，但必须让历史含义可理解。直接复用旧 id 表示另一件事，会让旧证据失去对象。

已经派给助手的任务更敏感。任务摘要、输入和写边界共同构成合同。主线程不能一边修改合同，一边希望旧助手按新意图交付。应先暂停或回收旧任务资格，再发布新合同；旧结果可以作为参考材料审查，但不能自动视为新任务的合格结果。

跨会话恢复时，任务包提供当前声明，现场提供实际状态。两者一致就继续；不一致就先修复可判断性。例如任务未勾而文件已存在，检查文件后决定是否完成；任务已勾而测试失败，回写问题并重新打开相关工作。恢复不是盲信文档，也不是盲信磁盘上的半成品，而是通过证据让二者重新对齐。

## 反模式：把任务包写成另一种聊天

**日志淹没任务。**每次调用工具都往任务文件追加一段经过，任务的 id、依赖和结果被埋在几十页叙述里。工具日志有自己的位置，任务包保留决策与状态。否则你只是把聊天换成 Markdown，恢复成本没有降低。

**待办项大如项目。**「完成后端」无法成为有独立边界的执行单元。它可以是阶段标题，不能是唯一任务。拆分依据不是文件数量，而是能否独立验证与合流。

**复选框代替证据。**把勾选当进度奖励，导致执行者在功能不完整时提前勾上。勾选应是结论，不是激励。没有证据就不完成，是为了让下一次恢复不依赖人的短时记忆。

**同一个状态写两遍。**把当前进度同时维护在任务文件和看板里，忘记更新其中之一。正确做法是从权威任务状态生成看板，而不是让看板成为另一位状态作者。

## 练习：制造三种错误，再观察拒绝

先在教学包中创建两个相互依赖的任务，运行 route，确认循环被拒绝。然后改成引用一个不存在的任务，确认得到缺失依赖错误。最后让下游任务勾选而上游仍未完成，确认检查器拒绝违反依赖顺序的完成声明。

这三种练习的重点不在错误文本是否好看，而在工具没有在不知道怎么做时随便选择一个任务继续。未知应该显式暴露，而不是被自动化包装成猜测后的确定性。

再为自己的真实需求拆五到八个任务。给每项写出输入、写边界、验证和依赖，请另一位工程师指出能并行的部分。若他的判断与你差异很大，回头检查共享接口与隐含依赖。一个好的任务包不保证两个人有同样的实现方案，但应该让他们对什么已经确定、什么仍未确定达成一致。

# 第 5 章 单线闭环：从一句话目标到可恢复执行

## 场景：周一的新会话不认识周五的你

周五结束时，陈默写完适配器，迁移工具还差失败队列。周一他开了新会话，只说「继续上次的迁移」。如果没有外部状态，这句话把一个几乎不可能的任务交给执行者：从有限摘要、当前文件和猜测里重建周五所有决定。

现在情况不同。新会话先看到任务包，知道 adapter 已完成且有测试证据，migration 未完成，integration 依赖它。它再检查工作区，发现迁移工具已有半成品，测试里仍有失败样本。接下来的合理动作不是重新规划整个迁移，而是验证现有状态，继续那一项未完成任务。

这就是可恢复执行的核心：恢复不要求记得过去发生的一切，只要求能够重新确认当前状态，并选择一个合法的下一步。本章把三件套串成单线闭环，同时解释为什么自动路由应该谨慎，而不是聪明地猜。

## 原则：从状态推动作，不从情绪推动作

### 单线先于多线

单线闭环指一个主线程对一个任务包负责，使用明确的集成分支推进。它并不禁止调用工具或临时助手；它强调只有一个最终合流与验收责任中心。共享边界由谁修改、状态由谁勾选、失败由谁处置，都不应存在歧义。

先建立单线，是因为恢复、验证和交付这些基本问题不会因增加助手消失。多线只是把问题复制多份，并加入协调成本。如果你还说不清一条工作流在哪个状态，就没有理由期待五条同时运行时更容易判断。

### 路由只做投影，不做第二套管理

路由器从文件计算下一阶段，不维护一份独立的「真实进度」。它的职责类似数据库视图：输入没变，输出应可重复；输入矛盾，就报告矛盾。它不能为了让用户看见进展而偷偷修改任务状态，也不能凭最近一条聊天猜测任务已经完成。

教学版的路由规则很小：范围是 draft 时进入 plan；范围 active 且有未完成任务时进入 execute；任务全部完成但验收未通过时进入 review；结构与验收一致时输出 ready-to-archive。这个最后状态只是准备就绪，不会自动移动目录或执行 Git 命令。

真实参考实现的分支绑定更严格。当前分支必须唯一对应活动包，无法匹配时不能选择最新目录兜底。显式传入包名可以帮助定位，但有写操作时还要复核分支所有权，避免读到正确包却把改动落到错误分支。

### 进展必须有现场证据

任务文件是当前工作声明，工作区是当前交付现场，二者需要对账。上个会话写了「测试通过」，新会话发现测试文件又被别人修改，就不能沿用旧结论。相反，文件已写好但任务还未勾，也不意味着必须从头重做。

恢复过程应该先收集只读证据：当前分支、差异、任务状态、已有产物和最新验证。然后做最小动作。越是不确定，越不应该先执行宽泛的修复命令。让未知减少，是恢复的第一项进展。

## 最小实现：一条可以中断的教学闭环

### 第一步：创建，而不是自动执行

```bash
python3 "$BOOK/examples/mini_harness.py" init photo-migration
python3 "$BOOK/examples/mini_harness.py" route photo-migration
```

初始路由应为 plan。打开三件套，替换示例范围与任务，确认适用于自己的练习项目。这里刻意要求一次明确的状态转换：把范围从 draft 改为 active。没有批准需求，就没有执行任务。

这不是安全沙箱，也不是法律意义的签名审批，只是协作式教学协议。它让「还在讨论」与「可以行动」在磁盘上有一个可见差别。生产系统需要更强审批时，可以由受控工具网关和审计系统承担，而不是给状态字段赋予它并不具备的权力。

### 第二步：一次只推动一个可验证变化

路由进入 execute 后，读取下一项 ready 任务的边界与 verify。实现者可以自己推理怎么改，但只能在批准边界内行动。遇到共享接口变动，先说明并更新合同，不把它藏进顺手修改。

完成适配器后，直接运行操作者批准的测试命令。验证失败就修复并重跑；验证成功后记录实际证据，再勾选任务。下一次 route 会计算出新的 ready 集合。你没有维护「当前任务编号」这种第二状态，因此重排任务不会让路由跳错位置。

最小运行循环可以用伪代码表达为：

```text
读取并验证任务包
如果范围未批准：停在规划
如果结构矛盾：报告具体错误，不执行
选择已满足依赖的未完成任务
读取边界与验证合同
执行一个有边界的子步骤
检查现场与验证结果
成功则记录证据并更新任务；失败则保持未完成
重新读取任务包，重新判断
```

这里没有调用模型的具体代码，因为本书教学层复用你已有的 Agent CLI 作为执行平面。完整的模型推理循环还包含消息管理、工具调用、预算和权限控制，不能由这几行路由伪代码替代。我们构建的是它外面的工程约束层。

### 第三步：从执行进入审核

当任务全部完成，路由转为 review。此时要看整条用户路径，不是再检查一次是否所有函数都有名字。对照片迁移，审核关注接口兼容、重复执行、失败恢复、源数据保护和改动边界。某项不满足，就把问题写回包，产生明确修复任务或重新打开相关任务。

不要把审核理解成给自己写一段表扬。它应该能发现任务拆分漏掉的东西。实现者按任务完成了所有局部模块，仍可能没有验证端到端行为。审核就是把局部结果重新放回原始目标下检查。

### 第四步：最终验证与交付准备

验收条目逐项满足后，填写实际证据，再运行 check。教学版 check 只核对文档结构与一致性，随后可运行最终 verify，由操作者给出测试程序和参数。

```bash
python3 "$BOOK/examples/mini_harness.py" check photo-migration
python3 "$BOOK/examples/mini_harness.py" verify photo-migration \
  --timeout 30 -- python3 -m unittest discover -s tests
```

验证记录包含命令、工作目录、退出码、时间、输出摘要与三件套摘要。它不会自动替你勾任务，也不会调用 Git。代码是否在验证后发生变化，仍需最终 diff 或源代码摘要检查。下一章讨论如何把这种证据边界说清。

## 中断恢复：三个不同的位置

### 在写文件之前中断

如果任务尚未产生改动，恢复相对简单：重新读合同，确认依赖和输入仍然有效，然后执行。不要因为旧会话已经「想好了」就跳过现场检查。计划可以失效，磁盘上的新事实可能改变最小路径。

### 在写文件之后、验证之前中断

这是最常见的位置。工作区存在部分结果，但没有完成证据。恢复者先检查差异是否在边界内，再运行限定验证。如果代码可用，可以承接它；如果状态混乱，做针对性修复。不应把未完成等同于全部无价值，也不应把文件存在等同于任务完成。

对写作任务，同样先检查章节标题、内容完整性和技术一致性。半篇章节不是完成品，但其中已通过审查的部分可以保留。重写一切只是最昂贵的恢复策略之一，并非唯一选择。

### 在外部副作用之后中断

假设对象上传已经成功，而数据库更新之前进程退出。Git 无法告诉你对象存储里究竟发生了什么，任务文件也不能替代查询。恢复程序必须根据稳定对象标识查询远端，对账后决定补写记录还是重新上传。

这要求在设计阶段安排幂等与可查询状态。不能等到事故之后才希望 Harness 通过阅读聊天恢复外部世界。控制平面能记录意图与证据，但不能凭空获得系统没有暴露的事务信息。外部操作越难撤销，执行前的设计越重要。

## 用恢复卡代替整段聊天

一张有效恢复卡可以很短：当前包名与分支，已完成的最后一项任务，当前任务剩余部分，最近验证，外部副作用状态，下一步禁止做的事情。它应引用正式状态，不复制一套独立进度。

例如陈默可以留下：「adapter 已验证；migration 写到失败记录分支，尚未验收；练习桶有本批对象，未操作生产；下一步先跑重复上传样本，禁止删除源照片。」这段话有用，因为它指向查询与验证，而不是要求接手者相信一段宏大总结。

本书恢复时也遇到过类似差异：前言与前两章已经写在磁盘上，任务包尚未记录写作完成；主线程重新运行章节验证，再补证据。另有 HUD 工作的未提交修改留在同一工作区，恢复不能根据旧文档里「已 stash」的文字假定工作区干净，而要查看实际 Git 状态并保护现有改动。

## 预算与停止条件也是闭环的一部分

可恢复执行不是永远不停止。一个好的循环知道何时应该继续、何时该暂停等待外部条件、何时必须拒绝下一步。常见停止条件包括核心范围仍不确定、当前任务身份不唯一、无关改动无法安全隔离、验证持续失败且需要外部系统信息、发布缺少权限。

还要限制重复尝试。相同命令在相同输入下连续失败，继续运行不会自动产生新信息。下一步应该是改变一个可检验假设、缩小失败样本或查询环境，而不是换一种语气让智能体再试。预算可以按时间、工具次数、成本或失败次数设定，关键是达到预算后产生清晰状态，而不是悄悄吞掉工作。

暂停报告应区分已完成产物与未完成交付。例如「源稿和 EPUB 已生成，但远端发布未执行」是一种清楚的状态；「基本完成，剩一点小事」则把权限、数据和交付层都混成了情绪词。下一位接手者需要的是对象与动作，不是乐观程度。

## 反模式：让自动化替你隐藏未知

**总是选择最新任务包。**修改时间会被格式化、复制和修复改变，与工作身份没有稳定关系。使用唯一绑定或显式标识，遇到歧义就停，不要把方便当正确。

**一条命令无限推进。**组合入口很有用，但如果没有中间证据和停止条件，它只会把多步错误连成更长的链。自动化程度越高，阶段边界越需要可观察。

**成功后沿用旧证据。**修复一个测试后又改了代码，却继续引用修复前的通过结果。证据必须对应最终输入，不能作为可反复使用的通行证。

**把暂停看成失败。**当外部授权缺失时停下，是正确控制。强行猜测、绕过门禁或抹掉阻塞才是失败。系统的目标是可靠推进，不是每次回答都显得顺利。

## 练习：刻意打断一次真实小任务

选一个可以在隔离仓库完成的小任务，在实现写到一半时关闭会话。新会话只能读取任务包、工作区和测试，不给它完整聊天历史。记录它用了哪些证据确认进度，是否重新做了已完成工作，是否知道下一步的写边界。

验收判据是：不依赖旧对话也能识别当前任务；不因文件存在而误勾完成；能指出尚未验证的部分；不会在未知外部状态下重复执行不可逆动作。恢复速度可以测量，但先确保恢复正确，再追求快。

最后修改一个已完成任务的输入，观察你是否会主动撤销旧证据的适用性。这个动作能检验你是否真正理解「状态来自当前事实」，而不是只学会了在任务列表上打勾。

# 第 6 章 机器门禁：不要相信「看起来完成」

## 场景：文件存在了，为什么仍然不算完成

本书最早写好的前言有场景、有读者承诺、有阅读说明。单独读它，并不像一篇未完成文章。但第一次运行章节验证时，程序拒绝了：缺少含「场景」「原则」「最小实现」「反模式」的必需标题。其他两章通过，前言没有通过。

这个失败没有证明前言写得差，只证明它不符合此前约定的结构。正确动作是对照合同审查：前言是否确实需要这些环节？既然本轮约定保留该结构，就把已有内容自然地组织到相应章节，而不是让校验器忽略前言。随后重新运行验证，才能记录当前通过。

这件小事展示了门禁最朴素的价值：让「我觉得已经可以了」遇到一个具体、可重复、能指出差异的检查。它也展示了门禁的边界：标题检查不知道观点是否准确，字数检查不知道段落是否水，构建检查不知道电子书是否会畅销。

## 原则：每一层检查只为自己的结论负责

### 结构检查

结构检查关注文件存在、字段合法、依赖无环、任务与验收一致、标题齐全等可确定规则。它们通常成本低，适合频繁运行。结构失败时，不应继续执行依赖这些结构的动作，因为系统连自己正在处理什么都不能可靠解释。

但结构完整不意味着内容真实。一段假证据同样可以符合字段格式，一个空洞章节同样可以有五个正确标题。结构门禁是必要条件之一，不是万能的真伪裁判。

### 行为检查

行为检查运行代码或构建，观察真实输入和输出。照片迁移要测试重复执行、上传失败、对账差异与接口兼容；教学 Harness 要测试循环依赖、虚假验收、超时和路径越界；电子书要检查构建命令及内部资源结构。

测试的价值不仅在成功样本，还在拒绝错误的能力。一个检查器如果对空输入也返回零，那么它的成功输出几乎没有信息量。先证明它会失败，再证明正确输入会通过，能显著提高你对测试本身的信任。

### 产品与语义检查

产品检查关注用户承诺是否实现。对本书而言，概念边界清不清、代码能不能照着运行、虚构案例有没有冒充事实、章节能否形成学习路径，都属于这一层。人工审核不可避免，但不能因此随意。明确审核对象、发现、修改和复查结论，就能让人工判断也具有可追溯性。

三层检查不必争夺「谁才是真正验收」。它们各自排除不同的失败。设计门禁时，应写清一个通过结果允许你作出什么决定，以及哪些决定仍需要其他证据。

## 最小实现：从可重跑命令到可审查证据

### 教学检查器的输入边界

打开 `book/examples/mini_harness.py`，先读 `documents` 和 `parse_tasks`，再读 `state`。顺序很重要：文件读取先验证常规文件与大小上限，任务解析再验证字段、标识和依赖，最后才计算状态。不应在还没有确认输入合法时猜测下一阶段。

教学版拒绝任务路径和输入文件为符号链接，拒绝越界包名，限制每份文档大小。这些限制减少误读和路径混淆，但在同一用户下存在恶意并发进程时，检查与读取之间仍可能有竞争窗口。因此它明确定位为合作式单写者教学程序，不声称提供敌对环境隔离。

状态计算拒绝「验收通过但任务未完成」，也拒绝完成任务没有证据。它不能鉴定任意自然语言证据真假。正式使用时仍应查真实测试输出与最终代码差异，必要时使用不可变构建输入摘要。不要把自然语言字段当密码学证明。

### 明确批准命令，而不是执行文档里的文字

任务文件中的 verify 是合同的一部分，但它可能由模型编辑。如果检查器自动把这段文字交给 Shell，就让内容作者获得了命令执行权。这里采用更明确的接口：操作者在命令行双横线后给出 argv，程序不从 Markdown 推导可执行动作。

```bash
python3 "$BOOK/examples/mini_harness.py" verify photo-migration \
  --timeout 30 -- python3 -m unittest discover -s tests
```

程序直接以参数数组启动子进程，不调用 Shell 解释。这样做避免了把分号、重定向或命令替换当额外动作，但仍不代表任意批准程序都安全。你批准运行的 Python 程序拥有当前进程权限；敏感环境应在受限工作区或工具网关执行。

教学版在 POSIX 平台为验证程序创建新会话，超时后终止进程组并等待回收；在其他平台只保证直接子进程终止。它没有宣称实现 Windows Job Object 级隔离，也没有磁盘配额。日志写到临时文件而不是无限内存管道，报告只读取有限摘要；极端噪声程序仍应在有配额的环境运行。

### 证据要包含对象身份

一份有用的证据至少应告诉你：运行了什么、在哪运行、什么时候运行、返回什么、对应哪些输入。教学日志记录 argv、cwd、returncode、时间、输出摘要和三件套内容摘要，并检查运行期间三件套没有变化。

这项检查防止的是验证中有人改变验收合同，不是自动覆盖全部源代码的新鲜度。若测试后源文件又被修改，必须再次验证，或者用源代码摘要与构建清单识别差异。很多「测试过了但上线坏了」的问题，本质上是通过证据与最终发布对象不是同一个对象。

证据文件采用临时文件加原子替换，避免写到一半留下损坏 JSON。但原子写入不等于多写者互斥。两个并发验证仍可能先后覆盖最近一次证据，因此教学版要求单写者。需要并行时，应引入运行标识、独立证据目录和明确合流规则，而不是假装原子替换解决了一切。

## 本书验证器：哪些自动化值得做

`verify_ebook.py` 最初承担四件事：骨架检查、章节结构检查、中文字符区间检查、Pandoc 构建。它的好处是简单，作者能快速知道哪一章缺失哪个环节。它的缺点也明确：只看文件大小无法判断 EPUB 内部资源是否完整，只看章节存在无法判断正文重复或技术描述不准确。

因此全书验收还需要两类补充。第一，运行伴随程序的独立测试，不让书里引用的代码只停留在排版状态。第二，检查电子书内部目录、清单和章节资源，确认构建产物不是一个名称正确的损坏文件。最后再做内容抽查：模型与控制平面的定义、权限边界、命令接口和未验证事实。

构建验证还应防止旧产物冒充新结果。如果本次构建失败，却仍在 dist 里留着上次成功的 EPUB，使用者可能误发旧书。更稳妥的实现先构建临时产物，成功验证后再替换正式文件；失败时明确报告，不用文件存在作为本次成功的证据。

字数规则也应说清口径。本书计数器统计 CJK 字符，不把英语代码、空格和标点都算进「汉字」。它是书稿厚度的粗指标，不是学习效果指标。正文内容必须通过编辑判断，不能为了让数字变绿插入重复段落。

## 故障注入：测试检查器是否值得相信

伴随测试全部在临时目录运行，不触碰真实仓库，也不访问网络。测试生命周期会创建草稿、激活范围、完成任务、填写验收，然后检查路由结果。故障用例则故意破坏依赖、填写矛盾验收、构造不存在的文件与路径逃逸。

超时测试运行一个睡眠程序，预算只有一秒，检查日志是否记录超时失败。命令数组测试把带分号的字符串作为参数传入，确认它没有被 Shell 解释成创建文件的动作。文档变化测试在验证期间修改范围文件，确认最终结果不被接受。

这些用例的共同点是小、确定、与真实失败模式对应。它们不是为了堆覆盖率，而是把容易被口头忽略的边界变成会报警的约束。读者可以运行：

```bash
python3 -m unittest discover -s "$BOOK/examples" -v
```

看到绿色之后，也要知道它没有测试什么：没有真实模型 API、没有生产照片迁移、没有跨机器协调、没有并发恶意进程隔离。诚实列出未覆盖领域，会让现有测试更可信，而不是更弱。

## 审核问题如何关闭

发现问题之后，不能只在最终回答列一串建议，让用户自己修。应把可执行问题回写当前任务包，修复，再重新运行相应检查。独立范围的问题可以形成后续任务包，但若当前承诺要求本轮闭环，就不能只建包不实施。

参考实现使用明确的处置类别：本轮修复、关联后续工作修复、接受风险、外部阻塞、不构成可执行问题。标签本身不负责正确性，证据才负责解释为什么可以关闭。接受风险需要说明风险与理由；外部阻塞需要指出具体依赖；不构成问题需要解释判断基础。

对本书而言，前言缺标题属于本轮修复；没有真实销量数据属于不能声称的市场结果，不是通过补一个测试就能消除的问题；远程发布权限不足则属于外部边界。把不同类型的问题混成「已处理」，会让项目状态再次失去可判断性。

## 反模式：通过结果也会被滥用

**零退出等于全对。**把一个狭窄检查的通过扩张为完整质量认证。解决办法是给每个检查写准确的覆盖范围，并在产品验收中补足其他层次。

**旧输出当通行证。**修复后没有重跑，却引用旧日志。证据不是勋章，它只对相应输入有效。最终改动改变了输入，就应重新获得证据。

**修改规则迁就结果。**检查失败时第一反应是降低阈值、删除用例或忽略文件。如果规则本身错了，可以调整，但必须明确为什么错，并保持原始目标成立。不能用隐藏失败的方式完成验收。

**执行不可信验证文本。**把助手自报命令当批准命令，或看到结果卡写 passed 就直接合入。验证应由主线程批准的工具在明确输入上独立运行，助手的陈述只是待核实证据。

## 练习：给每个绿色写一句边界说明

选你项目里三个最常见的通过结果，为每个结果补一句「它证明什么，不证明什么」。例如测试套件通过证明当前样本行为符合断言，不证明需求完整；构建成功证明工具链产物生成，不证明用户路径正确；结构检查通过证明任务包一致，不证明自然语言证据真实。

再设计一个负向样本，让每项检查真实失败一次。若很难想到让它失败的方法，考虑它是否真的检查了重要内容。把失败输出、修复和重跑结果放在同一份记录里，这比孤立的绿色截图更有解释力。

最后在验证通过之后，故意改变一个受测输入。观察你的收尾流程是否会要求重新验证。如果不会，门禁还缺少最后一块：把证据与最终交付对象绑定。下一章用 Git 把这个问题带到提交与发布边界。

# 第 7 章 Git 收尾：干净工作树、独立分支、提交与发布分离

## 场景：功能做对了，提交却做错了

迁移代码终于通过检查。陈默准备提交，习惯性敲了 `git add -A`。直到查看暂存差异时，他才发现里面还有前几天试验的日志修改、一份本地配置和另一项需求的半成品。功能是否正确与提交是否正确，是两件不同的事。

Git 不知道哪些修改属于当前目标。它忠实记录你选中的内容，不会因为提交信息写着「照片迁移」就替你排除缓存变化。这也是为什么 Harness 的工作不能在测试通过那一刻结束：最后还要把验证过的对象，准确地变成被保存和发布的对象。

本书写作现场就存在这种边界：电子书改动与另一项 HUD 工作同时出现在工作区。任务文档的旧陈述曾称 HUD 已被暂存隔离，但恢复时实际 Git 状态显示它仍有未提交修改。正确处置是相信现场、保留既有差异、只提交本任务路径，而不是为了得到干净状态把他人改动清空。

## 原则：Git 管对象，你管对象的含义

### 工作区、暂存区与提交是三个不同集合

`git diff` 通常显示工作区相对暂存区的差异；`git diff --cached` 显示暂存区相对 HEAD 的差异；`git status --short` 还会告诉你未跟踪文件。只运行一条 diff，就宣布「没有遗漏」，可能漏掉整个新建目录。

因此提交前至少要核对三件事：当前工作区有哪些修改，准备提交的集合是什么，还有什么未跟踪文件没有纳入或不应纳入。敏感配置、临时日志和构建缓存不应因为刚被创建就进入版本库。

### 一包一条集成分支

集成分支把任务包与改动集合关联。参考实现使用 `spec/` 前缀并在范围文件记录唯一绑定。它让路由、HUD 和收尾脚本知道当前工作属于哪个包，也让后来的人能从提交追到规格与验收。

分支绑定并不意味着物理隔离。两个分支若共用一个工作区，未提交改动仍可能随着切换保留。真正需要并行隔离时，优先使用独立 worktree 或工作目录，明确每个执行者在哪写。不能把「我开了分支」误读成「别人再也碰不到我的文件」。

### 保存、归档、提交、发布各有含义

保存只是文件落盘；归档表示任务生命周期结束并留下总结；提交把选定对象记录到本地历史；推送把引用与对象同步到远端；应用部署又是另外一步。它们可以被工具组合，但不能在报告里混为一谈。

尤其要把 done 与 push 分开理解。参考工作流的 done 负责验收后的归档与本地提交，push 负责后续合并、远端同步和分支清理。某些组合入口会在安全预检后继续 push，但这不取消中间的权限与状态检查。

## 最小实现：在独立练习仓库完成一次安全收尾

### 开始前先看现场

```bash
git status --short
git branch --show-current
git diff --stat
git diff --cached --stat
```

这些是观察命令，不会替你决定如何处置已有修改。如果发现与本任务无关的 dirty 内容，先明确归属。可安全隔离时使用独立 worktree；无法判断时保留原状并停止可能覆盖文件的操作。不要用 `reset --hard` 或大范围清理换一个漂亮的状态输出。

`stash` 是一种工具，不是自动保险。它可能没有包含未跟踪文件，也可能在恢复时产生冲突。使用前应知道保存了什么、用哪个标识恢复、恢复后怎样核对；不能把旧说明中的「已 stash」当作当前事实。

若需要为新任务建立隔离工作区，可以在练习仓库中使用明确分支名：

```bash
git worktree add ../photo-migration-work -b spec/photo-migration
```

若分支已经存在，这条创建命令会失败；应先查看现有 worktree 与分支归属，再决定附加到已有分支，而不是删除重建。恢复与创建不同，Git 层同样适用。

### 在暂存前限定路径

假设本次只允许修改存储实现、对应测试与教学任务包，暂存时明确写路径：

```bash
git add -- app/storage.py tests/test_storage.py .mini-harness/photo-migration/
git diff --cached --name-status
git diff --cached --check
git diff --cached
```

这里的路径是练习场景示例，实际项目应使用自己批准的边界。精确路径能减少误提交，但不替代逐块审查：同一文件可能同时包含两个任务的修改。若改动交织，需要按块暂存或在隔离目录构造只含当前任务的补丁。

暂存完成后还要再看未暂存差异。你可能已经审查了暂存版本，随后某个工具又改了源文件，导致测试运行的是新版本而提交的是旧版本。最可靠的办法之一，是在独立干净工作区验证将要提交或已经生成的提交对象，而不是模糊地说「这个目录测过了」。

### 运行最后一轮检查

对于教学包，先运行 check，再运行最终 verify；对实际项目，使用批准的测试和构建命令。把结果和最终改动对象关联起来。若检查后还做了修复，再检查，不能沿用修复前的成功日志。

本书的最终验证需要包含章节、示例、电子书构建和差异边界。字数达到阈值不能替代运行代码，代码测试通过也不能替代检查 EPUB。多层检查的成本通常远小于把错误版本交出去之后再解释发生了什么。

### 归档前确认没有悬挂助手

任务勾完不代表助手已经退出。一个迟到写作者或后台验证进程仍可能修改文件。归档前应确认结果已消费，活动身份已回收，旧身份不能再自动合流。否则你以为交付已经冻结，下一秒工作区又出现一份未经审查的结果。

参考实现把助手生命周期和任务完成分开管理：结果通过后还要合流与回收，归档会检查未清理运行。教学版没有助手调度，因此不自动处理这一步；如果你手工启了并发程序，仍要由操作者确认它们结束。

### 创建本地提交

完成审查后，提交命令应作为一个独立动作执行，不和前面修改文件的命令串成不可观察的长链。提交信息写清变化，并在使用参考工作流时附上任务包标识。

```bash
git commit -m "feat(storage): add object storage adapter" \
  -m "Spec: photo-migration"
```

这是练习格式，真实参考包应使用真实 slug。不要编造不存在的任务标识，也不要通过跳过钩子绕过失败。钩子失败时，保留当前成果，修复具体问题后重试。若失败涉及本任务之外的活动包或外部环境，报告准确阻塞，不修改别人的工作以便自己的提交变绿。

提交后用 `git show --stat HEAD` 和 `git show --name-status HEAD` 核对实际对象。提交信息是人的说明，树对象才是实际内容。二者不一致时，应在发布前修正，而不是希望读者只看标题。

## 发布是另一个授权边界

推送之前，查询远端状态，检查是否前移、是否受保护、是否允许当前用户发布。不要因为本地分支与 main 昨天一致，就假定今天仍能安全快进。远端变化意味着集成上下文改变，可能需要合并与重新验证。

```bash
git fetch origin
git log --oneline HEAD..origin/main
git log --oneline origin/main..HEAD
```

这些命令帮助理解关系，不自动决定发布。不同团队可能使用拉取请求、保护分支或发布审批；遵循现有机制，不让 Harness 另建一套绕过流程。自动脚本应保留清楚的预检与失败结果，而不是为了追求一条龙完成而强推。

如果推送失败，首先区分原因。认证失败需要外部授权；保护分支拒绝需要规定的评审入口；远端前移需要重新集成；网络中断则需要查询远端是否已收到。不要把它们都归成「重试即可」。特别是超时，不能从没有收到响应推定远端没有更新。

分支删除也必须等到合并已确认。一个名字看起来像旧分支，不意味着成果已在主分支。删除前核对包含关系与远端状态，失败时不要强删作为清理动作。项目的整洁应该建立在成果可追溯上，而不是建立在所有痕迹都消失上。

## 如何证明没有混入无关改动

有干净基线时，比较本任务提交与基线即可。工作区本来就 dirty 时，需要先保存已有差异的只读快照或摘要，再在本任务结束时核对它保持不变。这能证明没有触碰原有工作，但不能自动把混在同一行的修改分开。

本书的处理思路是限定到 `book/` 和当前任务包路径，并对恢复时已有 HUD diff 保存基线。最终检查要看暂存集合或提交集合，而不是要求整个仓库 `git diff` 为空。后者会把「不属于本任务的工作仍在」错误地当成需要清理的缺陷。

这也提醒我们，验收标准必须与现场相容。标准应表达「本任务没有引入或提交无关修改」，而不是不分归属地要求「整个工作区没有任何其他修改」。后者在多人或多任务现场可能推动危险的清空行为。

## 反模式：让收尾毁掉前面的正确性

**一把梭暂存。**看到测试全绿就 `git add -A`，把未跟踪配置、缓存和他人工作一起提交。准确选择路径只是第一步，逐块核对实际内容才是收口。

**为了干净而清空。**对无关 dirty 直接还原，认为这是良好工程纪律。真正的纪律是尊重已有成果，先分流，再执行限定操作。干净状态不是破坏权限。

**跳过钩子。**钩子不一定永远正确，但失败必须被解释与修复，不能用绕过让问题失去可见性。需要调整规则时，经过明确变更，不偷偷取消本次检查。

**本地完成冒充远端发布。**把构建、提交、推送和部署都叫「发布成功」。用户无法据此知道哪里可以拿到成果。报告应按对象与动作区分，不用一个大词覆盖四个状态。

## 练习：故意放入一项无关修改

在练习仓库里创建一项与任务无关的修改，再完成当前任务。要求自己最终提交仅包含批准路径，并证明无关修改仍完整保留。验证时同时看工作区差异、暂存差异与未跟踪文件，不只看其中一项。

接着在最终验证之后修改一个受测文件，观察收尾流程是否察觉证据已经过期。修正流程，让它重新验证或者拒绝交付。这个练习比背十条 Git 命令更接近真实事故，因为它检验的是对象是否一致。

最后模拟远端不可用，不进行强推或删除。写出准确结果：本地产物在哪里、本地提交是否存在、远端动作是否成功、外部阻塞是什么。能在失败处保持诚实和可恢复性，才算完成了 Git 收尾的工程训练。

# 附录 A 命令与阶段对照

## 场景：你需要的是下一步，不是更多命令

晚上十一点，迁移代码已经写完，测试也跑过了。陈默想结束工作，却面对三件不同的事情：把验收清单填写完整，把改动提交到本地分支，把版本送到用户面前。它们在日常语言里都可能叫「收尾」，在工程上却跨过不同的权限边界。混成一条命令之后，最容易发生的不是少做一步，而是多做一步：本来只想保留本地成果，却把未审核的版本发布出去。

这份附录帮助你判断当前需要哪个动作。它不是让你背一组命令，而是让你看到每个动作的输入、输出和不能替代的职责。书中有两套接口，必须先分清：参考实现 Spec Harness 使用 `.spec` 任务包与相应脚本；伴随教学程序 `examples/mini_harness.py` 使用 `.mini-harness` 和更小的固定格式。两者共享设计原则，不共享完整解析器，也不能直接交换文件。

如果你只想复现课堂实验，使用教学程序。如果你要研究参考实现，进入对应仓库，再查看本机脚本的帮助与当前版本文档。对话中的斜杠命令是宿主入口，不是所有终端都能执行的二进制。把 `/spec:check` 原样放进 Bash，通常只会得到找不到文件的错误。

## 原则：命令不赋予它原本没有的权限

一次命令调用的结果，最多能证明该命令实际检查或完成的事情。`route` 告诉你当前状态，不能证明功能可用；`check` 检查所定义的条件，不能证明产品有人购买；`commit` 记录本地对象，不能证明远端已经收到；`push` 同步远端引用，也不等于应用已经部署成功。定位问题时，要把每个动词拆回它真正改变的状态。

另一条原则是显式选择工作对象。多个活动任务包并存时，「最近修改」不是「本次任务」。如果工具无法把当前分支唯一映射到任务包，就应停止自动选择，要求明确包名。宁可多写一次参数，也不要拿另一项工作的通过结果给当前工作背书。

最后，区分可重跑和可重复产生副作用。状态查看一般可重跑；创建包会改变文件系统；执行验证命令可能发送网络请求；发布可能让用户看见新行为。对具有副作用的动作，重试前先查询上一次到底发生了什么。命令返回超时不代表远端没有完成操作。

## 最小实现：两套命令各走各的路

### 教学程序的四个动作

以下命令在独立练习仓库中运行。先把 `BOOK` 设置为本书目录的绝对路径，例如你克隆仓库后得到的 `book` 目录；这个变量是本地路径，不是在线下载地址。

```bash
export BOOK=/absolute/path/to/book
python3 "$BOOK/examples/mini_harness.py" init photo-migration
python3 "$BOOK/examples/mini_harness.py" route photo-migration
python3 "$BOOK/examples/mini_harness.py" check photo-migration
```

第一条创建初始草稿，不会帮你判断需求。第二条只读并显示状态。第三条在结构未完成时返回非零，这正是新项目的预期行为，不是安装失败。你应先修改范围文件，确认目标与非目标，把 `Status: draft` 改为 `Status: active`，再实施有边界的任务。

| 动作 | 读取 | 写入 | 成功结果的准确含义 |
| --- | --- | --- | --- |
| init | 包名和当前目录 | 三份初始文件 | 草稿已创建，已有目录绝不覆盖 |
| route | 三份文件 | 无 | 得到合法阶段与可执行任务，不执行任务文本 |
| check | 三份文件 | 无 | 结构达到 ready-to-archive；不等于功能测试已由它执行 |
| verify | 三份文件和操作者给出的 argv | evidence.json | 命令退出为零且运行期间三件套未改变 |

教学版接受 `plan`、`execute`、`review`、`ready-to-archive` 四种路由输出。`plan` 对应需求尚未批准；`execute` 对应有未完成的就绪任务；`review` 对应任务勾选完成但验收尚未通过；最后一种表示可以进入人工审查和归档准备，而不是脚本已经替你归档。

在任务实施过程中，你直接运行自己批准的测试命令，记录实际输出，再填写任务证据。三件套检查通过后，可以做一次最终验证：

```bash
python3 "$BOOK/examples/mini_harness.py" verify photo-migration \
  --timeout 30 -- python3 -m unittest discover -s tests
```

双横线之前是 Harness 的参数，之后是你批准执行的程序与参数数组。程序不从任务文件中取出命令自动执行，也不把数组交给 Shell 解释。因此，文件里即使出现要求上传秘密的命令，也只是一段需要审查的文字，不会因为你调用路由就运行。这里的保护范围很具体：防止不经批准执行任务文本；它不把你明确批准的程序变成无害程序。

`verify` 的日志只记录有限输出摘要和三件套摘要，不负责给操作系统上的子程序设置完整权限沙箱。教学版默认单写者；生产环境需要另行考虑配额、进程隔离和多写者协调。不要因程序叫 Harness，就推定它自动解决了全部运行时安全问题。

### 参考实现的阶段入口

下表按概念职责整理。实际安装的版本与宿主可能使用不同入口形式，应以当前帮助输出为准。

| 入口 | 何时使用 | 留下什么 | 不应顺带做什么 |
| --- | --- | --- | --- |
| new | 没有可恢复包且目标足够明确 | 新任务包、集成分支绑定 | 不带着未决的核心范围直接开工 |
| run | 范围已确定、有就绪任务 | 改动、验证证据、任务进展 | 不把助手的自报成功当最终验收 |
| check | 需要复核实现与范围一致性 | 可执行问题、处置与复跑证据 | 不把修复建议留给用户代做 |
| done | 当前任务通过验收 | 归档、完成摘要、本地提交 | 不因本地完成自动跳过推送预检 |
| push | 已有可发布的任务提交 | 合并与远端同步结果 | 不强推、不绕过保护、不混入活动包 |
| update | 范围或任务发生合法变化 | 明确的变更记录与新依赖 | 不抹去旧决定或迁就失败测试 |
| status | 想知道项目现状 | 只读状态 | 不把看板阅读当成执行或回收 |
| doctor | 安装或运行环境异常 | 环境诊断与限定修复 | 不顺手改业务需求与历史归档 |

`goal` 是组合入口，而不是第二种项目状态机。它把目标带入既有步骤，根据文件和验证结果继续推进。对于不可解决的外部阻塞，例如没有远程发布权限，组合入口必须如实停在阻塞处，不能用本地成功冒充远端成功。不同版本的组合入口是否自动进入 push，应阅读该版本命令契约，不从名字推断。

### 三个常见查询

**我只想恢复昨天的工作。**先看当前分支与工作区，然后路由，不要先新建同名目标。恢复时如果发现文件状态与旧摘要相反，优先查证文件与 Git 历史。旧摘要可以提供调查线索，但不是授权覆盖磁盘状态的依据。

**我改了任务拆分，要不要重新创建整个包。**通常不用。保留稳定任务标识，更新范围和依赖，记录为什么变化，重新验证受影响路径。若已经有运行中的助手，先回收旧合同再发新合同，避免旧助手继续交付已失效的任务。

**我只想保存进度，不想发布。**提交可以是本地检查点，但必须清楚它是否为未完成工作记录，不能把它描述为正式交付。工作流中的 done 通常具有更严格的完成语义。将「保存当前状态」和「宣告本次验收结束」写成两个明确意图，能减少很多误操作。

## 反模式：把查表变成跳步

第一种误用是「看到哪条命令短就用哪条」。在测试没跑过时直接调用归档命令，或者依赖组合命令替你猜测缺失范围，都是在用入口名称掩盖未完成的条件。门禁拒绝时，应该看它拒绝的具体条件，而不是换一个更宽松的入口试过去。

第二种误用是把旧教程当当前帮助。脚本的参数、默认行为和宿主适配都会演进。你可以从书里理解为什么要绑定分支，但不能据此推定某个未来版本仍接受同一组参数。对外部工具，先看版本和 `--help` 是核对接口，不是缺乏自信。

第三种误用是把命令输出粘贴成永久真理。上周生成的通过日志不能证明今天的文件仍然通过。日志必须带对象身份、版本或内容摘要，并与本次改动关联。否则日志只是一段曾经真实的话，已经失去当前授权价值。

## 练习：在按回车前说出副作用

给自己做一张三列表：准备运行的命令、它可能写入的对象、失败后如何确认副作用。至少填入一次状态查询、一次测试、一次提交和一次远端推送。判据不是每格都写「可重试」，而是能明确指出什么应该先查询再决定是否重试。

再做一个负向练习：新建教学包后立即调用 `check`。正确结果应是未通过。把它当作成功演练记录下来，因为它证明工具没有把草稿误判成完成。随后故意把验收改为 passed 而不勾任务，检查器应该拒绝这种自相矛盾。练习完成后恢复草稿，不把故障样本带入真实项目。

最后做一次口头交接：不看聊天，只给同事包名和当前分支，请他解释下一步该做什么、为什么不能直接发布。如果答案需要翻半小时的对话，继续补充磁盘上的状态与证据，而不是增加一条含糊的聊天摘要。

# 附录 B 制品与目录地图

## 场景：项目有很多文件，却没有明确的记忆

一个目录里堆满会议摘要、聊天导出、模型计划、工作日志和测试截图，并不意味着这个项目具有可恢复性。新会话进入之后，仍然可能不知道该读哪个文件。文件数量与项目记忆质量没有必然关系；如果两份计划都自称最新，它们甚至比没有计划更危险。

陈默在整理照片迁移任务时，把目录分成三个问题：哪些文件定义当前工作，哪些文件只是过去工作的证据，哪些文件属于可以清理的临时协调状态。这个分类看似朴素，却决定了恢复过程是查表还是考古。

本附录是一张职责地图。重点不是把所有路径记下来，而是认识文件所承担的语义。换一个 Harness 实现，路径可能变，三种职责仍然存在。尤其要警惕把展示文件当成真源：一个漂亮的看板可以从任务包生成，但不能反过来成为第二套进度记录。

## 原则：同一真源不是一个文件装下一切

同一真源说的是同一事实只有一个权威维护位置，不是整个系统只能有一个文件。范围写在范围文件，任务状态写在任务文件，验收结论写在验收文件；三者不互相复制同一个字段，才构成一致的任务包。把所有内容堆进一篇长文，不会自动得到一致性，反而会失去局部解析与局部更新的能力。

证据文件也有独立价值。测试输出、制品摘要、构建记录解释某次结论从何而来，但不应该靠一句「PASS」自行改变任务状态。主线程读过证据、核对对象与范围之后，才更新任务包。换言之，证据支持决定，不替代授权。

临时状态应被隔离，而不是被假装不存在。助手需要租约、心跳、输入卡片、结果卡片，这些都是真实运行状态；但它们不应让 Git 历史充满每秒刷新的噪声。把它们放进忽略目录，并不等于里面可以存放长期唯一成果。助手真正的交付必须被验证、合入正式路径，才成为版本库的一部分。

## 最小实现：从三份文件到一次可交接交付

### 教学目录

本书的教学程序采用单独目录名，刻意不伪装成参考实现的完整兼容版本：

```text
练习仓库/
├── .mini-harness/
│   └── photo-migration/
│       ├── spec.md
│       ├── tasks.md
│       ├── checklist.md
│       └── evidence.json
├── app/
│   └── storage.py
└── tests/
    └── test_storage.py
```

前三个文件定义工作，最后一个 JSON 由最终验证命令生成。JSON 内的内容摘要用于核对验证时看到了哪三份文档，不是对全部源代码的自动证明。源代码新鲜度仍要结合 Git diff、提交标识或额外的构建输入摘要核对。这一限制必须明说，否则读者容易把「文档未变」误读成「代码未变」。

| 文件 | 回答的问题 | 谁维护 | 什么时候读取 |
| --- | --- | --- | --- |
| spec.md | 要解决什么，不解决什么 | 主线程与需求负责人 | 每次恢复、范围改变、验收前 |
| tasks.md | 当前有哪些任务，什么依赖什么 | 主线程合流后更新 | 每步执行前后 |
| checklist.md | 是否满足验收，证据在哪里 | 最终审核者 | 检查、归档前 |
| evidence.json | 哪个命令在哪次快照上运行 | 程序记录，人工审查 | 验证后与交接时 |
| app 与 tests | 实际交付及行为断言 | 有授权的实现者 | 实现、测试、审查 |

教学版的证据文件会由下一次验证原子替换，便于观察最近一次结果，但这不是审计保留策略。需要完整历史时，应按运行标识保存不可变证据，并设保留期限。没有这个需要时，不必为了仿照大型平台而建立日志数据库；有这个需要时，也不要把覆盖式文件说成完整审计系统。

### 参考实现的目录

```text
参考仓库/
├── .spec/
│   ├── specs/
│   │   ├── YYYY-MM-DD_verb-object/
│   │   │   ├── spec.md
│   │   │   ├── tasks.md
│   │   │   └── checklist.md
│   │   └── archive/
│   └── docs/
├── .agents/
│   └── runtime/
│       └── helpers/
└── scripts/
```

这是职责示意，不是要求你的仓库逐字复制。参考实现的归档脚本还可能生成完成摘要、知识沉淀等文件；它们的确切形态以该版本实现为准。阅读时要区分两类变化：新任务包是一次新工作，归档是旧任务包完成后的存放位置变化。归档不应制造第二份仍然活动的任务包，否则路由会遇到重复身份。

`spec.md` 记录集成分支绑定，使工具能从当前工作分支找到当前包。多个包并存时，这比「选择最后修改的目录」可靠。分支不是任务内容本身，但它把工作流状态和 Git 的改动集合关联起来。绑定缺失、重复或与现场不符，都应该作为需要处理的状态，而不是由看板悄悄猜测。

`.agents/runtime/helpers/` 承担临时助手协调。输入卡片说明助手获批读取什么，任务卡片说明它负责什么，结果卡片记录它提交什么，租约与 fencing 信息约束何时仍具有协作资格。它们不能让主线程免于独立检查，也不能阻止同一操作系统用户下的恶意进程越权访问其他文件。权限隔离若属于需求，必须由另外的执行机制提供。

### 本书自己的制品

本书把可编辑章节与组装稿分开存放，原因不是喜欢目录，而是并行写作需要清晰的写所有权。三个人同时改一个巨大的 `book.md` 会频繁碰撞；各自写互斥章节，主线程统一组装，冲突少得多。

```text
book/
├── src/
│   ├── outline.md
│   ├── glossary.md
│   ├── 00-preface.md
│   ├── 01-agent-out-of-control.md
│   ├── 03-four-principles.md
│   ├── 04-task-package.md
│   ├── 05-single-loop.md
│   ├── 06-machine-gates.md
│   ├── 07-git-landing.md
│   ├── a-command-map.md
│   ├── b-artifact-map.md

│   └── book.md

│   └── test_mini_harness.py
├── metadata.yaml
├── verify_ebook.py
└── dist/
    └── from-zero-agent-harness.epub
```

章节文件是编辑真源，组装稿与 EPUB 是派生产物。修改文章应该回到章节，而不是直接修生成的 EPUB。否则下一次构建就会覆盖修改，造成「昨天已经改过，今天怎么又回来了」的困惑。派生产物可以入库也可以不入库，取决于分发方式；无论如何，重建路径必须明确。

`outline.md` 与 `glossary.md` 分别控制阅读顺序与术语。它们不应该被写作助手随意修改，因为改变这两份文件会影响每一章。它们是典型共享边界，应由主线程维护。各章的写作合同可以引用它们，但不因此获得改写权。

`metadata.yaml` 提供书名、语言、作者标识与描述。元数据属于出版内容，不应虚构发行成绩、认证或背书。`verify_ebook.py` 可以检查文件、标题、字数和构建结果，但不能替编辑确认论证质量。这就是为什么目录地图必须同时说明文件职责和验证边界。

### 交接包的最小内容

一次有效交接不需要把整段对话打包。它需要：任务包路径、集成分支或当前工作区位置、未完成任务、已验证命令、产物位置、明确的阻塞与禁止动作。接手者先复查现场，再决定是否继续执行；不要要求他无条件信任前一个会话的文字摘要。

对照片迁移任务，交接还需要数据侧状态：已迁移对象范围、对账结果、幂等键规则、失败队列位置。代码状态与外部状态不同步时，单独一个 Git 提交无法恢复全部事实。仓库能保存的是查询外部状态的办法与上次查询证据，而不是自动替外部服务保持一致。

对写书任务，交接需要已完成章节、术语约定、字数统计、未通过的检查、构建工具版本。没有外部数据库，也仍有环境依赖：机器上没有 Pandoc 时，Markdown 完整不意味着 EPUB 已生成。把这种依赖写清，比报一句「剩下只是打包」更有帮助。

## 反模式：五种目录上的自欺

第一种是双写真源。把任务进度同时写在 `tasks.md`、电子表格和看板文件中，却没有规定哪个字段由谁生成。只要一次更新漏掉一处，三个位置就会给出三个答案。解决方法是保留一个权威写入点，其余视图只读生成。

第二种是把临时工作区当交付。助手说文件写好了，主线程只保存它的路径，没有导入和检查。临时目录被回收后，唯一成果消失。交付必须经过正式路径合流，不能寄托在运行期缓存永远不清理的愿望上。

第三种是误清理。看到 `.agents` 就全删，以为都是无用数据；或者看到未跟踪文件就一并清空。临时目录也可能含尚未消费的结果。先查运行生命周期、确认无活动任务，再执行限定清理，不用宽泛通配符替代判断。

第四种是修改生成物。直接改 `book.md` 或电子书压缩包，不回写章节源稿。短期看问题消失，长期看构建不再可重放。正确修复位置是产生错误的最上游权威输入。

第五种是把所有东西纳入版本控制。高频心跳、临时日志、秘密凭证与正式任务文档混在一起，既污染历史又增加泄露风险。文件应不应该提交，取决于职责、敏感性和可重建性，不取决于它是不是刚被某个 Agent 创建。

## 练习：给每个文件标明主人

在你的仓库中挑十个与智能体工作相关的文件，分别标注「定义工作」「支持证据」「临时协调」「派生产物」。有些文件可能混合两种职责，这正是值得拆分或明确规则的地方。验收判据：每个事实都有唯一的权威维护位置，每个派生产物都能指出自己的生成输入。

随后做一次目录丢失演练，但只在练习仓库的复制品里进行。删除生成稿，尝试从章节重建；删除临时运行状态，确认正式交付仍可读取；保留任务包却删除聊天记录，观察你能否继续工作。如果某次删除导致关键事实永久消失，把那项事实迁到恰当的持久位置，再重做实验。

最后写一份不超过十行的交接说明。让接手者只凭说明找到当前任务、运行检查并识别一个故意留下的未完成项。能找到不是终点，能够不误判为完成，才是这份目录地图真正发挥作用的证据。

## 教学程序完整源码

以下源码与随书的 `examples/mini_harness.py` 一致。电子书独立阅读时，可保存为该文件运行；需要完整测试时使用随书源代码目录。本节是协作式教学控制层，能力边界见第 8 章与示例说明，不包含模型调用或生产存储业务。

```python
#!/usr/bin/env python3
"""A single-writer teaching harness. Commands never execute Markdown as code."""

from __future__ import annotations

import argparse
import hashlib
import json
import os
import re
import signal
import subprocess
import sys
import tempfile
from datetime import datetime, timezone
from pathlib import Path

FILES = ("spec.md", "tasks.md", "checklist.md")
LIMIT = 1024 * 1024
SLUG = re.compile(r"[a-z0-9]+(?:-[a-z0-9]+)*\Z")
ITEM = re.compile(r"^- \[([ x])\] (\S.*)$")
FIELD = re.compile(r"^  - (id|depends-on|boundary|verify|evidence): (\S.*)$")


class Invalid(ValueError):
    pass


def package(root: Path, slug: str) -> Path:
    if not SLUG.fullmatch(slug):
        raise Invalid("slug must be lowercase words separated by hyphens")
    base = root / ".mini-harness"
    path = base / slug
    if base.is_symlink() or path.is_symlink():
        raise Invalid("package paths must not be symlinks")
    return path


def documents(path: Path) -> dict[str, str]:
    result = {}
    for name in FILES:
        p = path / name
        if p.is_symlink() or not p.is_file():
            raise Invalid(f"missing regular file: {name}")
        if p.stat().st_size > LIMIT:
            raise Invalid(f"file exceeds 1 MiB: {name}")
        result[name] = p.read_text(encoding="utf-8")
    return result


def parse_tasks(text: str) -> list[dict]:
    tasks: list[dict] = []
    for line in text.splitlines():
        match = ITEM.fullmatch(line)
        if match:
            tasks.append({"done": match[1] == "x", "title": match[2]})
            continue
        field = FIELD.fullmatch(line)
        if field:
            if not tasks or field[1] in tasks[-1]:
                raise Invalid("orphan or duplicate task field")
            tasks[-1][field[1]] = field[2]
        elif line.startswith("  - ") or line.startswith("- ["):
            raise Invalid(f"malformed task line: {line}")
        elif line.strip() and not line.startswith("#"):
            raise Invalid("tasks.md accepts headings and task records only")
    if not tasks:
        raise Invalid("tasks.md has no tasks")
    ids = [t.get("id", "") for t in tasks]
    if len(set(ids)) != len(ids) or any(not SLUG.fullmatch(i) for i in ids):
        raise Invalid("task ids must be valid and unique")
    by_id = dict(zip(ids, tasks))
    for t in tasks:
        if not t.get("boundary") or not t.get("verify"):
            raise Invalid(f"{t['id']}: boundary and verify required")
        t["deps"] = [s.strip() for s in t.get("depends-on", "").split(",") if s.strip()]
        if len(set(t["deps"])) != len(t["deps"]) or any(d not in by_id for d in t["deps"]):
            raise Invalid(f"{t['id']}: duplicate or missing dependency")
    # Iterative topological validation avoids recursion limits on long chains.
    resolved: set[str] = set()
    while len(resolved) < len(tasks):
        batch = {t["id"] for t in tasks if t["id"] not in resolved and set(t["deps"]) <= resolved}
        if not batch:
            raise Invalid("task dependency cycle")
        resolved.update(batch)
    for t in tasks:
        if t["done"] and any(not by_id[d]["done"] for d in t["deps"]):
            raise Invalid(f"{t['id']}: completed before its dependency")
        if t["done"] and not t.get("evidence"):
            raise Invalid(f"{t['id']}: completed without evidence")
    return tasks


def single_field(text: str, name: str) -> str:
    values = re.findall(rf"^{re.escape(name)}: (.+)$", text, re.M)
    if len(values) != 1:
        raise Invalid(f"exactly one {name} field required")
    return values[0].strip()


def state(docs: dict[str, str]) -> tuple[str, list[dict]]:
    status = single_field(docs["spec.md"], "Status")
    if status not in {"draft", "active"}:
        raise Invalid("Status must be draft or active")
    tasks = parse_tasks(docs["tasks.md"])
    checklist = docs["checklist.md"]
    acceptance = single_field(checklist, "Acceptance")
    if acceptance not in {"pending", "passed"}:
        raise Invalid("Acceptance must be pending or passed")
    checks = []
    for line in checklist.splitlines():
        match = ITEM.fullmatch(line)
        if match:
            checks.append(match[1] == "x")
        elif line.startswith("- ["):
            raise Invalid("malformed checklist item")
    if not checks:
        raise Invalid("checklist must contain checks")
    complete = all(t["done"] for t in tasks)
    if acceptance == "passed" and (status != "active" or not complete or not all(checks)):
        raise Invalid("acceptance contradicts task or checklist state")
    if status == "draft":
        return "plan", tasks
    if not complete:
        return "execute", tasks
    if acceptance != "passed" or not all(checks):
        return "review", tasks
    if not single_field(checklist, "Evidence"):
        raise Invalid("acceptance evidence is empty")
    return "ready-to-archive", tasks


def hashes(docs: dict[str, str]) -> dict[str, str]:
    return {n: hashlib.sha256(t.encode()).hexdigest() for n, t in docs.items()}

def verify(path: Path, root: Path, command: list[str], timeout: int) -> int:
    if not command:
        raise Invalid("verify requires an operator-approved argv after --")
    before = documents(path)
    if state(before)[0] != "ready-to-archive":
        raise Invalid("finish structural check before final verification")
    # Output goes to temporary files, not an unbounded in-memory pipe.
    # This demo has no disk quota; run noisy tools in a quota-limited workspace.
    with tempfile.TemporaryFile() as out, tempfile.TemporaryFile() as err:
        process = subprocess.Popen(command, cwd=root, stdout=out, stderr=err, start_new_session=(os.name == "posix"))
        timed_out = False
        try:
            code = process.wait(timeout=timeout)
        except subprocess.TimeoutExpired:
            timed_out = True
            if os.name == "posix":
                try:
                    os.killpg(process.pid, signal.SIGKILL)
                except ProcessLookupError:
                    pass
            else:
                process.kill()
            process.wait()
            code = 124
        except KeyboardInterrupt:
            if os.name == "posix":
                try:
                    os.killpg(process.pid, signal.SIGKILL)
                except ProcessLookupError:
                    pass
            else:
                process.kill()
            process.wait()
            raise
        summaries = {}
        for name, stream in (("stdout", out), ("stderr", err)):
            size = stream.tell()
            stream.seek(0)
            summaries[name] = {
                "bytes": size,
                "truncated": size > 65536,
                "text": stream.read(65536).decode("utf-8", errors="replace"),
            }
    unchanged = hashes(before) == hashes(documents(path))
    report = {
        "timestamp": datetime.now(timezone.utc).isoformat(),
        "argv": command,
        "cwd": str(root),
        "returncode": code,
        "timeout": timed_out,
        "documents": hashes(before),
        "documentsUnchanged": unchanged,
        **summaries,
    }
    # Atomic replace prevents a torn evidence file, but is not a multi-writer lock.
    fd, temporary = tempfile.mkstemp(dir=path, prefix=".evidence-", suffix=".json")
    try:
        with os.fdopen(fd, "w", encoding="utf-8") as stream:
            json.dump(report, stream, ensure_ascii=False, indent=2)
            stream.write("\n")
        os.replace(temporary, path / "evidence.json")
    finally:
        Path(temporary).unlink(missing_ok=True)
    print(f"verify returncode={code} documentsUnchanged={unchanged}; {path / 'evidence.json'}")
    return 0 if code == 0 and unchanged else 1
```

# 附录 C 失败模式速查

## 场景：先停止扩散，再判断哪里出了问题

凌晨一点，终端上出现了第三次「已修复」，测试却仍然失败。最容易做出的反应是继续追问，让智能体再看一遍。这个动作几乎没有成本，于是可以无限重复；真正累积的成本躲在工作区里：每轮修复都改变了更多变量，下一轮排查面对的系统已经不是上一轮系统。

本附录不提供一个万能恢复命令。它提供的是排障顺序：先保护现场，确定本次任务身份，区分代码状态和外部副作用，再收集最小证据。每一种故障都应该缩小问题范围，而不是增加新的改动。你要恢复的是可判断性，而不是让终端继续滚动。

下面的速查表既适用于写代码，也适用于写这本书。代码会出现重复迁移，书稿会出现重复章节；代码会混入无关重构，书稿会混入未经授权的新主题。表面素材不同，失控的结构通常相似。

## 原则：把症状、原因和处置分开

「Agent 卡住了」是症状，不是原因。原因可能是模型请求没有返回、命令没有超时、助手没有续租、任务依赖尚未完成，或者它正在进行一个确实需要较长时间的计算。没有区分这些情况就强行重启，可能让两个执行者同时写同一组文件。

正确的故障记录至少包含五项：观察到的现象、受影响对象、最近一次确定成功的步骤、支持判断的证据、当前被禁止的动作。最后一项尤其有用。例如迁移对账未完成时，禁止删除源数据；助手身份失效时，禁止自动导入旧交付；分支绑定不确定时，禁止把最新任务包当当前任务包。

另外，不要把「可以接受风险」误解成「可以不写风险」。接受意味着明确风险范围、承担者、理由和撤销条件。测试失败如果揭示核心功能不成立，就不能靠 accepted_risk 这个标签变成成功；格式正确不等于决定合理。

## 最小实现：从症状定位到下一条有边界的动作

| 症状 | 优先核查 | 第一项有边界的动作 | 对应章节 |
| --- | --- | --- | --- |
| Agent 越改越偏 | 范围和非目标是否仍可见 | 对照范围列出越界文件，不继续添加功能 | 1、3 |
| 换会话重复做旧工作 | 任务状态是否带证据 | 读任务包，再查现场，不按旧摘要直接覆盖 | 4、5 |
| 所有任务都勾了却不能验收 | 检查清单和完成证据 | 运行当前检查，定位具体未满足项 | 6 |
| 检查器通过但产品不可用 | 检查覆盖了什么 | 增加一个真实用户路径的失败样本 | 6 |
| 无法选择当前任务包 | 分支绑定、重复包 | 显式确定任务身份，不挑最新目录 | 5、7 |
| 未提交改动越来越多 | 当前 diff 的归属 | 保存只读基线，分清本任务与已有改动 | 7 |
| 新助手拿不到上下文 | inputs 是否获批且可读 | 发布限定支撑文件，不给全仓扫描权限代替 | 8 |
| 助手说完成但主目录没变 | 结果是否已独立验证并合流 | 查交付状态与导入证据，不只读聊天 | 8 |
| 有 PID 却长期无进度 | 心跳、检查点、外部请求 | 查最近一次真实进展与超时条件 | 8 |
| 旧助手突然晚到交稿 | 身份、租约与摘要 | 拒绝自动合入失效身份，人工隔离复核 | 8 |
| 推送被拒绝 | 远程权限、分支保护、远端前移 | 查询远程状态，不强推绕过 | 7 |
| EPUB 构建失败 | 源文件、工具版本、构建错误 | 保留源稿，修复最小构建问题后重跑 | 6 |

### 一、范围漂移：不要先让模型「改回来」

当你发现缓存模块混入对象存储迁移，不要立刻给出「无关的全部回滚」这种含糊指令。文件可能同时包含本任务与已有工作，按文件整体还原会误删有效改动。先查看具体 diff，把本任务新增行、已有未提交行和未知来源行分开。

随后决定修复方式：若无关变化完全由本任务新增，可以做针对性补丁；若与其他工作的行交织，先隔离工作区或逐块人工核对。修复后重新验证迁移路径，不能只证明缓存变化消失。一次回滚也是一次改动，同样可能破坏功能。

写书时的同类故障是「为了讲清一个概念，另写了半本书」。处理方式不是机械删字，而是对照读者承诺判断那一节是否为完成学习目标所必需。必要的留，独立主题移出本轮范围，不能用长度指标代替编辑判断。

### 二、恢复断裂：先查询副作用，再重跑命令

假设上传进程超时，客户端没有得到成功响应。此时有两种世界：对象没有写入；对象已经写入，只是响应丢了。若恢复逻辑假定第一种世界，重试可能创建重复对象或重复记账。幂等键、目标查询和对账表的价值就在这里。

仓库任务也存在类似情况。一次提交命令可能已经创建对象，而界面没有显示最后输出。恢复时应查看当前 HEAD 与日志，再决定是否再次提交。不要从「我没看见成功」推导「它一定没做成」。没有可靠查询手段时，停止自动重试比盲目再来一次更安全。

写书的恢复相对简单，但仍要核对磁盘。章节已经存在而任务尚未勾选时，先验证现有内容，不应重新覆盖。同样，任务被勾选而文件缺失时，应把它视为状态矛盾并修复，不因复选框看起来漂亮就宣布完成。

### 三、假阳性验收：门禁只知道你教它检查的东西

一个按标题和字数检查的电子书验证器，无法判断段落是否重复、代码是否可运行或故事是否把虚构说成事实。它返回零并不撒谎；错误发生在使用者把一个狭窄结论扩张成了全书质量认证。

修复假阳性，需要补一条能覆盖真实缺口的检查，而不是把所有检查推翻。代码示例不可运行，就新增独立临时目录下的执行测试；章节有概念错误，就加入技术复核记录；EPUB 内部引用断裂，就解析压缩包结构和资源引用。每个新检查都应对应一种真实失败，避免不断堆叠无关规则。

同样要防假阴性。检索禁用词可能把讨论某种错误的正常说明也误判为错误。严格字符串匹配适合识别未完成模板，但不能天然理解语义。如果某项规则反复拦住正常内容，应该审查规则的边界与目的，而不是教作者绕着词汇写不自然的句子。

### 四、助手空转：先检查合同，再增加人数

助手没有输入时，启动更多助手只会得到更多空白思考。主线程应检查：任务目标是否具体，拥有的写路径是否明确，支撑文件是否真的发布到私有工作区，验证脚本是否能在该工作区运行。把一个主仓库绝对路径放进提示词，不等于助手获得了该文件。

当任务确实较长，检查点必须对应真实完成的子步骤。例如先完成一节并保存，再报告；不应让后台程序每秒写一个「我还活着」来伪装进展。长命令可以在明确的超时和租约约束下执行，长写作则应拆成可检查的小段。PID、心跳、产物、验证结果是四件事，任何一件都不能替代其他三件。

如果宿主连续失败或合同无法安全拆分，主线程接管是可接受结果。但必须如实记录没有获得并行交付，不能把「尝试启动」宣传成「多代理协作完成」。这条诚实边界既保护用户，也保护下一次排障所需要的事实。

### 五、发布阻塞：不要用危险动作换取一个绿色结尾

远程拒绝可能是权限问题，也可能是本地分支落后。两者处置完全不同。前者需要外部授权；后者需要合并、冲突处理和重新验证。无论哪种，都不应该用强推或跳过钩子换来一次看似成功的结尾。

本地已完成的成果不会因为推送受阻而消失。报告应明确区分：源稿已经写好，验证已经运行，本地提交是否存在，远端是否收到。用户可以接受真实的边界，却无法依靠一句混合了四层含义的「全部完成」做后续决定。

## 反模式：四个让排障变难的习惯

**换模型即诊断。**不同模型确实可能表现不同，但频繁切换会改变更多变量，掩盖原问题。先确认失败是否由上下文、任务合同、环境或验证造成，再进行受控的模型对照。一次换模型成功不能证明原结构没有问题。

**重启即恢复。**重启只结束进程，不恢复数据一致性。没有查询和幂等设计，重启后仍然面对同一个未知状态，有时还多了迟到结果。恢复能力来自状态设计，不来自重启按钮。

**增加日志即增加可观测性。**十万行无任务身份的日志不如十行带包名、任务标识和输出摘要的记录。日志应帮助回答明确问题，不该要求读者重新看完一次会话才能理解故障。

**把失败归咎于执行者。**助手不读不存在的输入、检查器不验证未编码的标准，都是合同层面的缺口。说一句「下次认真点」不会改变它们。修复应落到输入、边界、状态转换或验证机制，而不是停留在人格化批评。

## 练习：建立你自己的故障样本库

在独立练习仓库里做三次小故障。第一次删除一个任务依赖的标识，让路由拒绝；第二次把未完成任务的验收改为通过，让一致性检查拒绝；第三次让验证命令睡眠超过超时，让日志记录超时失败。每次只改变一个变量，并保留触发条件、实际输出和恢复方法。

参考判断如下：缺失依赖属于规格错误，应修任务关系，不应强行派发；验收与任务矛盾属于状态错误，应修真实进展而不是改检查器；超时属于执行结果，先查副作用再决定重试。三种故障都返回失败，但它们对应三个不同层次，不能用一个「重试」按钮处理。

再从真实工作中选一次失败，写一张不超过一页的故障卡。避免写情绪评价，只写可重现条件、观察、最小修复和防回归检查。你的 Harness 成熟度不会由配置文件数量体现，而会由这些失败是否不再以同样的方式反复发生体现。

读到这里，不必记住整本书的所有规则。记住一个操作习惯就够了：每次准备继续之前，确认你知道现在在哪、下一步改什么、怎样知道它做对了。如果三问答不齐，就先修结构；答齐之后，再让智能体发挥它擅长的推理与执行能力。
