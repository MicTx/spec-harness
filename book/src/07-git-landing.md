# 第 7 章 Git 收尾：干净工作树、独立分支、提交与发布分离

门禁已经证明任务满足约定，最后仍有一个容易被忽略的对象边界：哪些文件真的属于这次交付？本章把验证过的对象安全地落到分支、提交和发布动作上。

## 场景：功能做对了，提交却做错了

迁移代码终于通过检查。陈默准备提交，习惯性敲了 `git add -A`。直到查看暂存差异时，他才发现里面还有前几天试验的日志修改、一份本地配置和另一项需求的半成品。功能是否正确与提交是否正确，是两件不同的事。

Git 不知道哪些修改属于当前目标。它忠实记录你选中的内容，不会因为提交信息写着「照片迁移」就替你排除缓存变化。这也是为什么 Harness 的工作不能在测试通过那一刻结束：最后还要把验证过的对象，准确地变成被保存和发布的对象。

本书写作现场就存在这种边界：电子书改动与另一项 HUD 工作同时出现在工作区。任务文档的旧陈述曾称 HUD 已被暂存隔离，但恢复时实际 Git 状态显示它仍有未提交修改。正确处置是相信现场、保留既有差异、只提交本任务路径，而不是为了得到干净状态把他人改动清空。

## 原则：Git 管对象，你管对象的含义

### 工作区、暂存区与提交是三个不同集合

`git diff` 通常显示工作区相对暂存区的差异；`git diff --cached` 显示暂存区相对 HEAD 的差异；`git status --short` 还会告诉你未跟踪文件。只运行一条 diff，就宣布「没有遗漏」，可能漏掉整个新建目录。

因此提交前至少要核对三件事：当前工作区有哪些修改，准备提交的集合是什么，还有什么未跟踪文件没有纳入或不应纳入。敏感配置、临时日志和构建缓存不应因为刚被创建就进入版本库。

### 一包一条集成分支

集成分支把任务包与改动集合关联。参考实现使用 `spec/` 前缀并在范围文件记录唯一绑定。它让路由、HUD 和收尾脚本知道当前工作属于哪个包，也让后来的人能从提交追到规格与验收。

分支绑定并不意味着物理隔离。两个分支若共用一个工作区，未提交改动仍可能随着切换保留。真正需要并行隔离时，优先使用独立 worktree 或工作目录，明确每个执行者在哪写。不能把「我开了分支」误读成「别人再也碰不到我的文件」。

### 保存、归档、提交、发布各有含义

保存只是文件落盘；归档表示任务生命周期结束并留下总结；提交把选定对象记录到本地历史；推送把引用与对象同步到远端；应用部署又是另外一步。它们可以被工具组合，但不能在报告里混为一谈。

尤其要把 done 与 push 分开理解。参考工作流的 done 负责验收后的归档与本地提交，push 负责后续合并、远端同步和分支清理。某些组合入口会在安全预检后继续 push，但这不取消中间的权限与状态检查。

## 最小实现：在独立练习仓库完成一次安全收尾

### 开始前先看现场

```bash
git status --short
git branch --show-current
git diff --stat
git diff --cached --stat
```

这些是观察命令，不会替你决定如何处置已有修改。如果发现与本任务无关的 dirty 内容，先明确归属。可安全隔离时使用独立 worktree；无法判断时保留原状并停止可能覆盖文件的操作。不要用 `reset --hard` 或大范围清理换一个漂亮的状态输出。

`stash` 是一种工具，不是自动保险。它可能没有包含未跟踪文件，也可能在恢复时产生冲突。使用前应知道保存了什么、用哪个标识恢复、恢复后怎样核对；不能把旧说明中的「已 stash」当作当前事实。

若需要为新任务建立隔离工作区，可以在练习仓库中使用明确分支名：

```bash
git worktree add ../photo-migration-work -b spec/photo-migration
```

若分支已经存在，这条创建命令会失败；应先查看现有 worktree 与分支归属，再决定附加到已有分支，而不是删除重建。恢复与创建不同，Git 层同样适用。

### 在暂存前限定路径

假设本次只允许修改存储实现、对应测试与教学任务包，暂存时明确写路径：

```bash
git add -- app/storage.py tests/test_storage.py .mini-harness/photo-migration/
git diff --cached --name-status
git diff --cached --check
git diff --cached
```

这里的路径是练习场景示例，实际项目应使用自己批准的边界。精确路径能减少误提交，但不替代逐块审查：同一文件可能同时包含两个任务的修改。若改动交织，需要按块暂存或在隔离目录构造只含当前任务的补丁。

暂存完成后还要再看未暂存差异。你可能已经审查了暂存版本，随后某个工具又改了源文件，导致测试运行的是新版本而提交的是旧版本。最可靠的办法之一，是在独立干净工作区验证将要提交或已经生成的提交对象，而不是模糊地说「这个目录测过了」。

### 运行最后一轮检查

对于教学包，先运行 check，再运行最终 verify；对实际项目，使用批准的测试和构建命令。把结果和最终改动对象关联起来。若检查后还做了修复，再检查，不能沿用修复前的成功日志。

本书的最终验证需要包含章节、示例、电子书构建和差异边界。字数达到阈值不能替代运行代码，代码测试通过也不能替代检查 EPUB。多层检查的成本通常远小于把错误版本交出去之后再解释发生了什么。

### 归档前确认没有悬挂助手

任务勾完不代表助手已经退出。一个迟到写作者或后台验证进程仍可能修改文件。归档前应确认结果已消费，活动身份已回收，旧身份不能再自动合流。否则你以为交付已经冻结，下一秒工作区又出现一份未经审查的结果。

参考实现把助手生命周期和任务完成分开管理：结果通过后还要合流与回收，归档会检查未清理运行。教学版没有助手调度，因此不自动处理这一步；如果你手工启了并发程序，仍要由操作者确认它们结束。

### 创建本地提交

完成审查后，提交命令应作为一个独立动作执行，不和前面修改文件的命令串成不可观察的长链。提交信息写清变化，并在使用参考工作流时附上任务包标识。

```bash
git commit -m "feat(storage): add object storage adapter" \
  -m "Spec: photo-migration"
```

这是练习格式，真实参考包应使用真实 slug。不要编造不存在的任务标识，也不要通过跳过钩子绕过失败。钩子失败时，保留当前成果，修复具体问题后重试。若失败涉及本任务之外的活动包或外部环境，报告准确阻塞，不修改别人的工作以便自己的提交变绿。

提交后用 `git show --stat HEAD` 和 `git show --name-status HEAD` 核对实际对象。提交信息是人的说明，树对象才是实际内容。二者不一致时，应在发布前修正，而不是希望读者只看标题。

## 发布是另一个授权边界

推送之前，查询远端状态，检查是否前移、是否受保护、是否允许当前用户发布。不要因为本地分支与 main 昨天一致，就假定今天仍能安全快进。远端变化意味着集成上下文改变，可能需要合并与重新验证。

```bash
git fetch origin
git log --oneline HEAD..origin/main
git log --oneline origin/main..HEAD
```

这些命令帮助理解关系，不自动决定发布。不同团队可能使用拉取请求、保护分支或发布审批；遵循现有机制，不让 Harness 另建一套绕过流程。自动脚本应保留清楚的预检与失败结果，而不是为了追求一条龙完成而强推。

如果推送失败，首先区分原因。认证失败需要外部授权；保护分支拒绝需要规定的评审入口；远端前移需要重新集成；网络中断则需要查询远端是否已收到。不要把它们都归成「重试即可」。特别是超时，不能从没有收到响应推定远端没有更新。

分支删除也必须等到合并已确认。一个名字看起来像旧分支，不意味着成果已在主分支。删除前核对包含关系与远端状态，失败时不要强删作为清理动作。项目的整洁应该建立在成果可追溯上，而不是建立在所有痕迹都消失上。

## 如何证明没有混入无关改动

有干净基线时，比较本任务提交与基线即可。工作区本来就 dirty 时，需要先保存已有差异的只读快照或摘要，再在本任务结束时核对它保持不变。这能证明没有触碰原有工作，但不能自动把混在同一行的修改分开。

本书的处理思路是限定到 `book/` 和当前任务包路径，并对恢复时已有 HUD diff 保存基线。最终检查要看暂存集合或提交集合，而不是要求整个仓库 `git diff` 为空。后者会把「不属于本任务的工作仍在」错误地当成需要清理的缺陷。

这也提醒我们，验收标准必须与现场相容。标准应表达「本任务没有引入或提交无关修改」，而不是不分归属地要求「整个工作区没有任何其他修改」。后者在多人或多任务现场可能推动危险的清空行为。

## 反模式：让收尾毁掉前面的正确性

**一把梭暂存。**看到测试全绿就 `git add -A`，把未跟踪配置、缓存和他人工作一起提交。准确选择路径只是第一步，逐块核对实际内容才是收口。

**为了干净而清空。**对无关 dirty 直接还原，认为这是良好工程纪律。真正的纪律是尊重已有成果，先分流，再执行限定操作。干净状态不是破坏权限。

**跳过钩子。**钩子不一定永远正确，但失败必须被解释与修复，不能用绕过让问题失去可见性。需要调整规则时，经过明确变更，不偷偷取消本次检查。

**本地完成冒充远端发布。**把构建、提交、推送和部署都叫「发布成功」。用户无法据此知道哪里可以拿到成果。报告应按对象与动作区分，不用一个大词覆盖四个状态。

## 练习：故意放入一项无关修改

在练习仓库里创建一项与任务无关的修改，再完成当前任务。要求自己最终提交仅包含批准路径，并证明无关修改仍完整保留。验证时同时看工作区差异、暂存差异与未跟踪文件，不只看其中一项。

接着在最终验证之后修改一个受测文件，观察收尾流程是否察觉证据已经过期。修正流程，让它重新验证或者拒绝交付。这个练习比背十条 Git 命令更接近真实事故，因为它检验的是对象是否一致。

最后模拟远端不可用，不进行强推或删除。写出准确结果：本地产物在哪里、本地提交是否存在、远端动作是否成功、外部阻塞是什么。能在失败处保持诚实和可恢复性，才算完成了 Git 收尾的工程训练。
