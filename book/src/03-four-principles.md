# 第 3 章 四条原则：显式假设、最小实现、边界清晰、验证优先

## 场景：一份正确却没有用的范围文档

陈默写下了第一版范围：「改善照片存储的可靠性，提升性能，保持良好的用户体验。」这句话没有错误，也几乎没有约束力。采用对象存储可以符合它，重写整个后端也可以符合它；增加缓存可以符合它，替换数据库同样可以符合它。一个目标如果能为互相冲突的十种方案辩护，就还没有成为可执行的规格。

他把文档发给智能体，得到了一份雄心勃勃的规划：多区域部署、分层缓存、图片去重、缩略图服务独立化。每一项都能解释为什么有价值，但加起来已不是原来那件两三天的工作。问题并非智能体恶意扩张，而是目标函数过于宽泛：当「更可靠、更快、更好」是全部约束，任何增加复杂度的方案都能自证合理。

把文档写实，不是把所有设计细节提前规定死。你需要给推理留空间，同时把不可随意改变的东西说清。本章的四条原则就是为这件事服务：显式假设让认知可审查，最小实现限定投入，边界清晰限定改动，验证优先限定完成含义。

## 原则：四个问题，四种约束

### 显式假设：把确定、推定和待决分开

事实是已经获得支持的陈述，例如代码当前用磁盘路径保存照片。假设是为了推进工作而暂时采用的前提，例如现有照片总量在一个夜间窗口内可以完成迁移。待决项则是不能合理代替负责人决定的选择，例如是否允许某些付费用户经历短暂停写。

三者最大的区别不是措辞，而是变化时如何处理。事实被推翻，需要修正调查结果；假设被推翻，需要触发预先约定的重规划；待决项没有答案时，某些任务不得启动。若混在一段散文里，智能体很容易把一个暂时估计当永久授权。

| 类别 | 陈默的表述 | 如何验证或处理 |
| --- | --- | --- |
| 事实 | 当前上传接口返回本地照片标识 | 查看路由与接口测试 |
| 假设 | 一次批次可以迁移五百个对象 | 在练习数据上测量耗时与失败率 |
| 待决 | 是否允许迁移期间删除源照片 | 本轮默认禁止删除，不替用户授权 |
| 非目标 | 不重构缓存模块 | diff 中检查相关路径无新增改动 |

显式并不意味着把问题全抛给用户。工具库、目录命名、日志格式等可合理选择的细节，给出默认值与理由即可。只有答案会改变整个项目形态、无法合理假定或需要外部权限时，才应该停下来问一个聚焦问题。无限提问也是一种失控：工作看似谨慎，却没有产出。

假设还应附带失效信号。例如「若试迁移显示单批耗时超过窗口预算，先减小批次并重新估算，不自动转向分布式调度」。这样写，执行者知道什么时候继续、什么时候调整、什么时候必须重新决定。一个假设没有失效条件，就容易变成无人察觉的永久事实。

### 最小实现：减少独立变化，不减少正确性

最小实现经常被误解为「先不处理失败」。对照片迁移而言，这是最危险的节省方式。幂等、对账和保留源数据不是豪华功能，而是让迁移能够恢复的最低条件。真正可以省的是尚未需要的多区域调度、插件系统与独立缩略图微服务。

判断一个部件是不是最小范围，可以问：去掉它，核心承诺是否仍成立？去掉多区域部署，仍能把本地存储迁移到对象存储；去掉对象校验，可能把损坏的数据标成成功，核心承诺就不成立。最小方案应缩减可变性，而不是缩减责任。

另一个实用办法是写「暂不引入」清单。这不是永久否决，而是在本次目标下限制新增机制。先让一个对象正确上传、查询与回退，再批量处理；先让一个真实工作流可恢复，再考虑多 Agent 协作。每增加一个独立服务，就增加一组需要解释的状态、部署和失败方式。

对本书而言，最小交付是可读源稿、电子书构建与能复现的教学程序。不需要同时建立在线学习平台、付费墙或视频课程。电子书是否畅销还依赖定位、渠道、价格与真实读者反馈，不能用文件数量或字数指标替代市场结果。

### 边界清晰：分别说明可以读什么、可以改什么

任务的 boundary 首先是改动边界。让存储适配器任务修改 `app/storage.py` 和对应测试，并不意味着它有权修改全部配置。若执行过程中发现必须调整一个共享接口，应提出具体变更理由，由主线程批准或重新拆任务，而不是把「相关」当成无限扩大权限的词。

读取边界与写入边界也不同。助手可能需要读接口声明、术语表和验证脚本才能工作，但它不需要改这些共享文件。在并行写书中，目录与术语表是输入，章节文件是输出；把两者都写成「属于你」，就会引发多方同时改变约定。

边界还有强弱之分。Markdown 中的限制属于协作协议；受信任的执行者应遵守，但普通文件本身不会阻止越权系统调用。需要强制隔离时，要通过工作区、进程账户、容器、文件权限或工具网关限制实际能力。不要把一句「禁止访问」描述成已经实施的操作系统防线。

路径边界不能替代语义边界。一个任务只允许修改两份文件，仍可能在这两份文件里重写整个产品逻辑。因此审查既要看文件名，也要看差异内容是否服务目标。自动路径检查帮你缩小审查面，不帮你做完全部审查。

### 验证优先：先说明看到什么才相信

写 verify 不是让人未写代码先猜实现，而是提前确定可观察结果。比如「上传同一照片两次，得到稳定对象标识，数据库不产生重复记录；模拟对象存储失败，接口返回受控错误且源数据仍在」。这些都是行为，不绑定某个内部类名。

一个好的验证合同还包括反例。只看成功上传，不能证明重试正确；只看 EPUB 文件存在，不能证明内部章节顺序正确；只看任务复选框全勾，不能证明证据属于当前版本。负向样本告诉你门禁是否真的会拒绝不合格输入。

验证优先也不意味着所有判断都自动化。文字是否易读、场景是否可信、设计是否对准用户需求，都可能需要人工审查。关键是让人工审查有明确对象与结论，不要一句「看过了」涵盖全书。机器检查结构，测试检查行为，编辑检查内容，各自报告自己的边界。

## 最小实现：把宽泛目标改成可执行范围

把陈默原来的三句愿望，改写为下面这份范围。它仍没有规定每一个函数怎么写，但已经足以排除大部分无关方案。

```markdown
# 照片迁移范围

Status: active

## Goal
已有上传接口改用 S3 兼容对象存储，保持响应字段不变。
提供可重跑的迁移工具；迁移成功须通过对象与记录对账。

## Facts
当前上传接口、路径规则和接口测试已经查明。

## Assumptions
先在隔离的练习数据集验证，再决定真实数据批次。
若批次超时或发现对象不一致，停止扩大批次。

## Non-goals
不重构缓存，不更换数据库，不删除源照片。
不在本轮引入多区域部署或独立图片服务。

## Acceptance
上传接口兼容测试通过。
重复迁移不产生额外记录。
故障时保留源数据并输出可查询的失败项。
最终 diff 可追溯到当前任务。
```

这里的英语状态字段服务教学解析器，中文正文服务读者。二者各有所长：机器解析少量固定结构，人和智能体理解剩余语义。不要为了机器方便，把整个需求变成难读的配置语言；也不要为了自由排版，让状态字段出现五种拼法。

下一步不是直接把这篇文档交给执行者就不管，而是做一次反向推演。假设智能体要重构缓存，能否从范围中找到授权？不能。假设它提出保留源照片以便失败恢复，是不是范围外扩张？不是，那是核心正确性要求。假设它认为需要一个新服务，是否有权自行部署？没有，应解释为什么最小方案不足。

这种推演可在五分钟内完成，比写一页「务必遵守以上要求」更有用，因为它检验的是约束有没有区分能力。没有区分能力的规格，看起来详尽，执行时仍然任人解释。

### 用本书做一次目标拆解

「写一本畅销电子书」混合了可控制的产物目标与不可直接控制的市场结果。合理的工程转换不是承诺销量，而是把当前可验收的承诺列出来：面向有编程经验的读者、用一个持续案例解释 Harness、提供真实可运行的教学程序、每章有练习、源稿可构建为 EPUB、明确技术适用边界。

字数区间是一种防止交付过薄或无节制扩张的辅助约束，不是文学或商业质量评分。若为了达到下限重复段落，即使计数器通过，产品审查仍应失败。若章节很短但讲得完整，也应该在明确修改范围后决定是否接受，而不是悄悄降低阈值迁就当前稿件。

同样，自动化只能检查已定义的东西。书中的人物必须标明为教学虚构；技术例子不能声称拥有未实现的安全隔离；未运行的代码不能写成已验证。把这些内容写入审查合同，才是对「可售技术书」的负责方式。

### 审查一次变更请求

陈默在实现中发现原来所有照片路径都拼在一个公共函数里，迁移必须改这个函数。此时应该提交一个小而完整的变更说明：现有边界为什么不足，拟增加哪个文件，哪些任务会受到影响，如何验证旧调用方没有退化。主线程批准后更新范围和任务，再实施。

不要把变更审批理解成写作业等盖章。小项目里主线程可以当场判断并记录；复杂项目里则可能需要负责人授权。共同点是决定先于执行，而且决定能在换会话后被找到。没有记录的口头许可，到了下一次恢复又会变成两个版本的记忆。

## 反模式：四条原则也会被滥用

**假设墙。**罗列几十条假设，既没有证据也没有失效条件。结果不是更透明，而是没人知道哪三条决定系统成败。优先写会改变范围、正确性或成本的假设，其他日常细节不必上升为正式风险。

**最小借口。**把错误处理、数据校验、资源回收都推到「下一版」，却把非必要界面和插件系统塞进第一版。最小方案首先要成立，然后才谈规模。一个会丢照片的最小迁移器，不是最小可行，是最小不可用。

**边界魔法。**认为写了允许路径就获得了强制安全保证，或者因为路径在允许列表就不再审查语义。边界同时需要协作约定、实现限制与最终核对，三者没有任何一个能独立完成全部职责。

**验证表演。**验收里写「测试通过、代码优雅、用户满意」，没有具体命令或判据。这类文字只能宣布态度，不能区分成功与失败。改成能被第三方重复观察的结果，才有工程价值。

## 练习：让四条原则互相检查

挑一个真实需求，先写一页范围，再对它做四轮检查。第一轮，把每条未证实陈述标成假设并写失效信号。第二轮，删去不影响核心承诺的机制。第三轮，列出写边界和必需读取输入。第四轮，为每个完成承诺写一个成功样本和一个失败样本。

参考判据是：一个新会话能够明确回答本次不做什么；一个实现者能在不被规定全部内部设计的前提下动工；一个审核者能指出哪条观察会让他拒绝验收。如果这三个角色仍要依赖你在旁边不断解释，文档还需要收紧。

最后故意提出一个范围扩张，例如把图片去重加入迁移任务。写下接受和拒绝各自的理由。正确答案不是永远拒绝新需求，而是能够说明它是否属于同一个目标、会改变哪些依赖、需要增加什么验证。四条原则约束的是决定的清晰度，不是把项目冻结成一块石头。
