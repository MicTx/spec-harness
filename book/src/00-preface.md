# 前言：为什么 Agent 需要 Harness

## 场景：你经历过的那种夜晚

十一点，你对着终端里的智能体说：「帮我把存储迁到对象存储。」它利落地列了计划，然后开始改代码。头两个小时一切顺利，你甚至有点感动。第三个小时，它顺手「优化」了一个跟迁移毫无关系的模块；你让它改回来，它道歉，改回了大部分。第四个小时，上下文窗口到了尽头，你开了一个新会话，把之前的对话摘要贴过去——它读完，自信地继续，然后把你两个小时前已经改对的文件又改了一遍。凌晨两点你按下 Ctrl-C，面对工作区里四十多个被改动的文件、一半跑通的迁移脚本和三片说不清状态的测试，你意识到一件事：**没有人，包括你自己，能说清这次工作现在处于什么状态。**

第二天你在社交平台上写：「模型还是不够聪明。」点赞的人很多。但你心里知道不完全是这样。模型其实相当聪明——每一次单步操作它都做得像模像样。出问题的是别的东西：目标只存在于对话里，对话会消失；完成从来没有定义过，所以永远无法被证明；改动没有边界，所以什么都会被牵连进去。

这类事故不一定能靠更强模型消除，其中很大一部分是**结构问题**。模型能力仍然重要，但结构上的缺口需要结构性的补足。

## 原则：三个立论

这本书的全部内容建立在一组判断上，先把它们摆在明处，你合不合意，一眼可断：

**一、先检查结构，再判断模型能力。**更强的模型可能减少错误，但不能保证持久状态、授权边界和验收机制自动成立。意图没有载体、上下文会清零、完成没有判据、改动没有边界——这四个洞是过程结构上的，堵洞要用结构。

**二、文件是真源，对话不是。**凡是重要的——范围、决定、进度、验收标准——必须落到比会话更持久的载体上，而且必须落到机器可解析的形态。会话用来干活，不用来记事。谁说了算？磁盘说了算。

**三、完成必须可证明。**「完成」不是一种感觉，是一个可验证的断言：跑了什么命令、得到什么退出码、留下什么证据。不可证明的完成，一律按未完成处理。

本书把由这三个立论构建的工程约束层称为 **Harness 的控制平面**。行业中的 Harness 含义更宽，还可能包含工具执行、上下文管理、预算与权限等运行时能力；本书聚焦其中可恢复、可验证的工程工作流，不把它当作唯一或完整定义。一个比喻：智能体是一台马力惊人的发动机，Harness 是围绕它的车架、方向盘、仪表盘和刹车。没有车架的发动机当然也能转，喷着火苗，非常壮观，但你没办法开着它去任何地方。发动机越强，车架越重要——这不是悖论，而是这本书全书的立论。

读完这本书，你将能够：

- 用一条清晰的因果链解释自己的项目为什么会返工，而不是归咎于「模型变笨了」；
- 在自己的仓库里，用 Markdown、Python 标准库和 Git，从零理解并运行一个仅用标准库的最小工作流 Harness；
- 为一次跨会话的复杂工作建立「范围、任务、验收」三件套，让新会话根据文件与现场证据接上进度；
- 用机器门禁代替「看起来完成了」，用退出码和证据关闭任务，而不是用印象；
- 把一次复杂改动安全地落进 Git——干净的工作树、独立的分支、提交与发布分离；
- 判断什么时候值得请临时助手并行干活，什么时候该由主线程一个人接管。

## 反模式：这本书不做什么

为了让「是什么」更清晰，先把「不是什么」划出来。以下四种期待请提前收回：

- **不是提示词大全。**提示词影响一次调用，Harness 约束整个过程。两者不冲突，但这本书只讲后者。如果你在找「一句话让模型听话」的咒语，这本书会令你失望。
- **不是模型评测。**不会告诉你哪家模型更强，也不讨论采样参数。执行平面可替换是本书原则，为它写排行榜没有意义。
- **不是某个 CLI 的操作手册。**书里会出现命令，但命令是证据，不是主角。原则写在正文，命令细节收在附录。换一个工具，原则原样成立。
- **不是多智能体炫技。**并行助手只在边界干净、值得拆分时出场，而且我们会专门花一节讲什么时候**不**该拆。先用单线闭环把失控治住，再谈编队。

## 贯穿案例：这本书自己

技术书最尴尬的局面，是书里讲的方法连作者自己都不用。这本书不打算这样。

本书从立项、拆任务、写章节到导出电子书，使用书中讲的工作流管理：它有自己的任务包（范围、任务、验收三件套），有自己的校验脚本——每个章节必须包含「场景、原则、最小实现、反模式、练习」五个环节、正文字数必须落在设定区间、电子书必须能由脚本真实构建出来，任何一项不满足，整个项目的验收检查就退出非零。你会在各章看到这个任务包的真实片段：范围怎么冻结、任务怎么拆、门禁怎么拦住不合格的章节、无关改动怎么被挡在提交之外。

写书是一次真实的适用性实验，不是对任意重构的保证。数据迁移、并发执行与敏感权限仍需要各自的工程设计。

同时，伴随教学程序只用 Python 标准库，测试在隔离临时目录运行；Git 与 EPUB 构建另有工具依赖。正文中的配置片段用于说明协议，不等于已实现照片业务。教学版与参考实现共享原则，但不共享完整能力或文件格式。

## 假设的读者

你应该已经满足这三条：

1. 会用至少一个支持工具调用的编程智能体（能读写文件、执行命令的那类，而不只是聊天窗口）；
2. 熟悉 Git 的日常操作：分支、提交、合并；
3. 有一台能跑 Python 3.9 以上版本的机器。

不需要你带团队——书里的主角就是一个独立开发者；但第 8 章会讨论两三个人的小团队怎么共用这套结构。也不需要你先读过任何 Agent 框架文档，这本书从失控的第一性原因讲起。

## 如何读这本书

全书八章加三个附录，建议按顺序读，因为每一章都在为你的最小 Harness 添加一个部件，章与章之间是叠加关系：

- 第 1 章解剖失控：把「AI 越改越偏」翻译成四个结构性缺口。这是诊断学。
- 第 2 章给出总图：控制平面、执行平面、验证层、交付层四层结构，以及 Harness 的定义。这是解剖学。
- 第 3 章是四条设计原则：显式假设、最小实现、边界清晰、验证优先。此后每一章都在反复应用它们。
- 第 4 章建任务包：范围、任务、验收的三件套，复杂工作的同一真源。
- 第 5 章串单线闭环：从一句话目标到可恢复执行，中断之后接得上。
- 第 6 章上机器门禁：用退出码和证据关闭任务，不再相信「看起来完成」。
- 第 7 章做 Git 收尾：干净工作树、独立分支、提交与发布分离。
- 第 8 章把 Harness 装进你的项目：一晚上完成最小接入，并知道何时引入并行助手。
- 附录 A 是命令与阶段对照，附录 B 是制品与目录地图，附录 C 是失败模式速查——它们是工具页，供你读到一半或读完之后回来翻。

每章固定五个环节：**场景**（一个具体的项目事故）、**原则**（这一部件的设计逻辑）、**最小实现**（你可以照抄的代码与约定）、**反模式**（命了名的常见错误）、**练习**（在你自己的仓库上动手）。如果你是精读型读者，建议每章的练习当章做完——这套东西的手感只能在键盘上长出来。

一个阅读提醒：正文里反复出现一个词——**真源**（single source of truth）。每当看到它，问一句「此刻谁说了算」：是对话说了算、记忆说了算，还是磁盘上的文件和脚本的退出码说了算。这个问题是全书的暗线。

## 最小实现：开工前的准备

读这本书是动手课，不是听讲课。开工前把环境备齐，后面每章的「最小实现」才能当章落地。陈默、拾光相册以及涉及用户数量、时间、事故的情节均为教学虚构，不是用户调研、实测或商业背书：

- **Python 3.9 或更高版本。**伴随教学 Harness 使用标准库，无需第三方 Python 包；构建电子书另需 Pandoc。用 `python3 --version` 确认。
- **Git。**第 7 章之前的练习也需要你随时能开分支、看 diff。
- **一个支持工具调用的编程智能体。**任何能读写文件、执行命令的 CLI 都行——这是执行平面，具体哪家不影响正文。
- **一个真实的练习仓库。**最好是你在维护的真项目，哪怕是私人小项目；不必专门造一个玩具仓。书中所有练习都指向你自己的仓库，真实仓库给的反馈，玩具仓给不了。

准备一个空目录也行：附录 B 给出 Harness 的完整目录地图，第 8 章有一晚上的最小接入清单。工具就绪后翻页——我们从陈默的一个糟糕周末开始。
