# Templates

`scripts/init_spec_package.py` renders the first ` ```markdown ` fence under each `## \`<file>\`` heading: `spec.md` (LITE, default), `spec.full.md` (FULL, rendered as `spec.md` with `--workflow full`) and `tasks.md`. `completion-summary.md` is generated by `complete_spec_package.py`. Change only these fences when changing init output.

Headings are matched by stable keys (`scripts/spec_package_support.py`, `SectionKey`): the Chinese title, its English alias, or an anchor such as `<!-- spec:open-questions -->`. Replace every placeholder before `run`.

## `spec.md`

```markdown
# [项目名称] - 项目范围

<!-- spec-format: 2 -->

## 1. 问题定义
- **项目目标**：一句话描述项目要解决什么问题

## 2. 假设与待确认

### 2.2 关键假设
- 假设 A

### 2.3 待确认问题
- [ ] 问题 A

## 3. 功能范围

### 3.3 不在范围内
- 明确列出本轮不做的内容

## 4. 最小实现路径
- 最简单可行方案：xxx

## 5. 技术决策
- Workflow: LITE
- 证据协议：evidence: runs
- Git integration branch：`spec/YYYY-MM-DD_<slug>` 或适用外理由

### 5.1 验证策略
- 范围级别：package
- 快速检查：<变更对象对应的局部测试/静态检查命令>

## 6. 成功标准与验证方式
- [ ] 标准 A 达成 -> verify: task_0001

## 7. 风险与约束
- 无
```

LITE rules:

- `项目目标` is one sentence; `关键假设` lists only premises whose failure would change the plan; `2.3` lists open questions or the single line `- 无`.
- `5.1`: `范围级别` is `package` (default), `integration` (also fill `集成检查`) or `project` (also fill `集成检查` and `全项目检查`). `快速检查` is a real command.
- Each `## 6` criterion names the task whose `verify` proves it; tick it only after that verify passed.

## `spec.full.md`

```markdown
# [项目名称] - 项目范围

<!-- spec-format: 2 -->

## 1. 问题定义
- **项目目标**：一句话描述项目要解决什么问题
- **目标用户**：谁会使用这个产品或系统
- **核心价值**：完成后能持续提供什么价值
- **Literal ask**: <verbatim request>
- **Stated purpose**: <purpose|unknown>
- **Inferred outcome**: <result>; confidence: <high|medium|low>; evidence: <source>
- **Constraints and exclusions**: <constraints|unknown>
- **Trade-off preference**: <speed|quality|cost|maintainability|unknown>

## 2. 假设与待确认

### 2.1 已确认事实
- 事实 A

### 2.2 关键假设
- 假设 A

### 2.3 待确认问题
- [ ] 问题 A

### 2.5 已证伪路径
- 无

## 3. 功能范围

### 3.1 核心功能（MVP）
- [ ] 功能 A：描述

### 3.3 不在范围内
- 明确列出本轮不做的内容

## 4. 最小实现路径
- 最简单可行方案：xxx
- 暂不引入：xxx
- 不做的抽象/配置化：xxx

### 4.1 方案阶梯
- B0 | literal ask | <compare>
- B1 | minimal change | <compare>

Recommendation: B0 because <reason>. Flips if A1 is FALSIFIED.

## 5. 技术决策
- Workflow: FULL
- 技术栈：xxx 或适用外
- 证据协议：evidence: runs
- 本轮允许改动：xxx
- 本轮不应触碰：xxx
- Autonomy: medium
- Git integration branch：`spec/YYYY-MM-DD_<slug>` 或适用外理由

### 5.1 验证策略
- 范围级别：package
- UI surface: <changed|unchanged>
- 快速检查：<变更对象对应的局部测试/静态检查命令>

<!-- spec:correction-log -->
### 5.5 修正日志
- none.

<!-- spec:deviation-log -->
### 5.6 偏离日志
- none.

## 6. 成功标准与验证方式
- [ ] 标准 A 达成 -> verify: task_0001

## 7. 风险与约束
- 风险点：xxx -> 缓解措施
```

FULL adds, on top of LITE:

- Key assumptions as `A<n> | statement | kind: intent|system|external | evidence | CONFIRMED|UNVERIFIED|FALSIFIED | if false: <impact>`.
- `4.1`: `B0` is the literal ask, `B1` the smallest useful change; add `B2`/`B3` only for a materially different option. The recommendation names its flip assumption.
- `UI surface: changed` requires `- Browser check: \`<command>\`` repeated in a machine task `verify`.
- `5.5` gets one row (`| round | approach | result | new information |`) per failed correction round; a round without new evidence means change strategy, a second one goes to the owner. `5.6` records deviations from the literal ask as `D<n> | literal ask | actual | reason | reversibility | authority`.
- External facts that can change the plan (versions, API behavior, pricing) are recorded with a source URL and date under an optional `### 2.6 外部事实`.

### Pending questions

`2.3` has one markup: an open question is a plain `- [ ]` line; an answered one is `- [x]` plus `| answer: <结论>`.

```text
- [ ] 本地格式用哪一种？
- [x] 选用本地解析器 | answer: 沿用现有 JSON 解析
- [ ] [decision] 是否允许发布结果？
```

`[decision]` marks the questions that require user authority (permission, irreversible actions, preferences, external dependencies): it closes only with both `answer:` and `| authority: user:<reference>`. A non-placeholder answer closes any other question; Git writes, credentials, global configuration, publication and destructive external actions are always `[decision]`. The single line `- 无` means there are no pending questions.

## `tasks.md`

```markdown
# [项目名称] - 任务拆解

## 使用规则
- 每个任务写 `boundary`（可改什么）和 `verify`（首个反引号内是可直接执行的命令；无法机器验证写 `verify: manual: <理由>`）
- 有先后时写 `depends-on: task_0001`；跑过 verify 才能勾选
- 发现的可执行问题追加为新任务，本轮做完

## 阶段一：实现
- [ ] 实现核心功能 A 的最小闭环
  - boundary: 只改该功能主链路所需模块
  - verify: `python3 -m pytest -q tests/test_core_feature_a.py`（替换为本项目真实测试命令）
- [ ] 打通关键链路
  - depends-on: task_0001
  - boundary: 只补集成所需粘合代码，不顺手重构
  - verify: `python3 -m pytest -q tests/test_critical_path.py`（替换为本项目真实集成验证命令）
```

Task rules:

- One task, one passable verification. A `verify` command carries what it needs to run (directory, preconditions); a template command left in place fails on purpose.
- `verify` never calls this package's own check gate. Real credentials never appear in `boundary`, `verify` or evidence; use placeholders such as `<admin-token>`.
- Optional `id: task-name` gives a stable identity. Never reorder checked tasks; append new ones in a new section with explicit ids.
- Evidence: `python3 scripts/spec_verify.py run --root <project> --slug <slug> --all` records `runs.jsonl`; `check` and `done` need each machine task's latest record to pass on the current worktree. Rerun `--all` after any change.

## Success criteria

`## 6. 成功标准与验证方式` is the acceptance surface: every criterion is `- [ ] <criterion> -> verify: task_XXXX`, and `check`/`done` require all criteria ticked, all tasks done and passing runs evidence. An empty §6 fails.

Legacy v1 packages that still carry `checklist.md` keep their checklist gates until migrated; `init` never renders one.

## `completion-summary.md`

Generated by `complete_spec_package.py`; it must contain the v1 `## 问题处置` JSON (`{"version": 1, "issues": []}`, non-empty via `--issue-disposition`). Distillation is an optional `## AGENTS.md 增量提议` diff fence (`--agents-proposal`), never applied automatically and never written to global or user-level files.
