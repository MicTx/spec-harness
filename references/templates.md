# Templates

Templates are executable contracts in prose. Read only the two init fences below by default. `scripts/init_spec_package.py` parses the first ` ```markdown ` fenced block of `spec.md` / `tasks.md` under `## \`spec.md\`` / `## \`tasks.md\``; `checklist.md` is no longer part of the init template (legacy v1 packages keep theirs — see the legacy contract below); `completion-summary.md` is generated by the script, so never hand-write a second full template. Replace every placeholder before execution and keep `boundary`, `verify`, and acceptance evidence tied to a real check. When changing the init templates, change only these two fences.

Section identity is language-neutral: every gated heading carries a stable machine key (`scripts/spec_package_support.py`, `PACKAGE_SECTION_KEYS`), matched through its Chinese or English alias or an HTML key anchor such as `<!-- spec:open-questions -->` on or directly above the heading line; display titles are localization, never contract. New packages carry the `<!-- spec-format: 2 -->` marker (spec.md fence): `### 2.3 待确认问题` is checkbox-structured — `- [ ]` is an open question, ticking the line (optionally with an inline `→ 结论`) closes it; packages without the marker keep legacy free-text parsing. v2 packages get no `checklist.md`: acceptance is judged from `spec.md` §6 success criteria plus the executable evidence protocol.

## `spec.md`

```markdown
# [项目名称] - 项目范围

<!-- spec-format: 2 -->

## 1. 问题定义
- **项目目标**：一句话描述项目要解决什么问题
- **目标用户**：谁会使用这个产品或系统
- **核心价值**：完成后能持续提供什么价值

## 2. 假设与待确认

### 2.1 已确认事实
- 事实 A

### 2.2 关键假设
- 假设 A

### 2.3 待确认问题
- [ ] 问题 A

### 2.4 可选解释与取舍
- 当前选择：xxx -> 理由

### 2.5 已证伪路径
- 无（暂无证伪记录；条目写：方案概述 + 证伪依据出处 + 日期）

## 3. 功能范围

### 3.1 核心功能（MVP）
- [ ] 功能 A：描述

### 3.2 扩展功能
- 无

### 3.3 不在范围内
- 明确列出本轮不做的内容

## 4. 最小实现路径
- 最简单可行方案：xxx
- 暂不引入：xxx
- 不做的抽象/配置化：xxx

## 5. 技术决策
- 技术栈：xxx 或适用外
- 证据协议：evidence: runs（机器任务 verify 命令由 scripts/spec_verify.py run 真实执行并记录 runs.jsonl；无命令任务写 `verify: manual: <理由>`；verify 命令不得自引用本包 check 门禁）
- 本轮允许改动：xxx
- 本轮不应触碰：xxx
- Git integration branch：`spec/YYYY-MM-DD_<slug>` 或适用外理由

### 5.1 验证策略
- 范围级别：package
- 变更对象：本任务包 boundary 涉及的模块、入口和数据契约
- 快速检查：<变更对象对应的局部测试/静态检查命令>
- 集成检查：适用外：本轮没有直接受影响的跨模块用户路径
- 全项目检查：适用外：本轮不涉及共享基础设施、跨模块契约或发布载荷；由发布门禁统一执行
- 升级触发：只有改动共享基础设施、跨模块契约、构建/依赖、发布载荷，或 package/integration 检查暴露跨边界回归时，才把范围升级并记录理由

## 6. 成功标准与验证方式
- [ ] 标准 A 达成 -> verify: task_0001
- [ ] 标准 B 达成 -> verify: task_0002

## 7. 风险与约束
- 风险点：xxx -> 缓解措施
```

Writing requirements:

- `2. 假设与待确认` (assumptions & open questions) must not be empty; write uncertainties down.
- `4. 最小实现路径` (minimal implementation path) must have at least 3 items and answer "why not more this round".
- Do not put optional governance headings into the default package.

When tasks depend on each other, declare `- depends-on: task_0001, task_0002` (comma-separated positional IDs) under the dependent task; execution follows dependencies, reordering must keep the IDs in sync, and without a declaration tasks stay independent.

## `tasks.md`

```markdown
# [项目名称] - 任务拆解

## 使用规则
- 每个任务都要写清楚 `boundary` 和 `verify`；机器任务的 verify 以首个反引号 span 为执行的命令
- 如果一个任务没有验证方式，就不能开始；确无命令可执行的任务写 `verify: manual: <理由>`
- 发现的可执行问题必须回写本包，并在本轮做完
- 新任务包使用 `YYYY-MM-DD_<verb>-<object>`，详见 `references/naming-and-commits.md`
- verify 命令不得自引用本包 check 门禁（自指命令在「最近一条」语义下不可满足）

## 阶段一：实现
- [ ] 初始化最小项目骨架
  - boundary: 只创建必须目录、依赖和启动骨架
  - verify: `python3 -m pytest -q tests/test_skeleton.py`（替换为本项目真实初始化验证命令）
- [ ] 实现核心功能 A 的最小闭环
  - depends-on: task_0001
  - boundary: 只改该功能主链路所需模块
  - verify: `python3 -m pytest -q tests/test_core_feature_a.py`（替换为本项目真实测试命令）
- [ ] 打通关键链路
  - depends-on: task_0002
  - boundary: 只补集成所需粘合代码，不顺手重构
  - verify: `python3 -m pytest -q tests/test_critical_path.py`（替换为本项目真实集成验证命令）

---

**当前进度**：由脚本计算，无需手动维护
```

Writing requirements:

- The template ships only implementation tasks: branch creation is init's job, document sync happens at `done`, and the minimal-review point is a §6 success criterion — never re-add boilerplate tasks for them. Stage names express delivery order; one task carries one `boundary` / `verify` pair.
- Verify is two-way by construction: a machine task writes its command as the first backtick span of `verify` (later spans are prose and never execute); a task that cannot be machine-verified writes `verify: manual: <reason>`. In `evidence: runs` packages a verify line that is neither is a contract error the check gate reports, never guessed intent.
- Complete verify recipe (write the probe away at authoring time — a verify line carries everything the executor needs, so execution never guesses the environment): ① 运行目录 run directory — where the command runs, or the command `cd`s itself; ② 前置条件与依赖 preconditions and dependencies — env vars, services, fixtures, prior tasks (`depends-on`); ③ 完整可执行命令 full executable command — the first backtick span is copy-and-run, no `<todo>`, no ellipses; ④ 成功判定 success criteria beyond exit 0 — expected output or assertions, when they exist; ⑤ 失败处理 failure handling — expected failure shape and where to look, when it exists. Existence-based, never a five-item form: a missing element must genuinely not exist.
- Task granularity law: one task equals one passable verification; prerequisites belong in the task line, never left for the executor to probe. 禁止合并无关 boundary 减少轮次 — shrinking rounds by merging unrelated boundaries is forbidden (the `new` stage's directory-audit split rule stays in force).
- Executable evidence (`evidence: runs`, the template default): run machine verifications with `python3 scripts/spec_verify.py run --root <project> --slug <slug> --task <id>` (or `--all`); each run appends one JSON line to the package's `runs.jsonl`. `check` and `done` require every machine task's latest record `exit == 0` with a `tree_fp` equal to the current worktree fingerprint (`.spec/` paths excluded): a missing record fails 未验证, a moved tree fails 证据过期 — re-run the recorder after the last change to restore the gate. Hollow commands (`true`, `:`, bare `echo`) and a verify that invokes this package's own check gate are refused before they can fake a pass; full gate contract: `references/stages/check.md`.
- The paths and commands above are pre-project examples and authorize nothing; replace them with real boundaries and verification commands that prove delivery before execution — a left-in-place template command fails instead of passing vacuously, which is deliberate. Run the `verify`-described check before ticking a task; never check off an unrun verification.
- Migration/upgrade tasks (moving, merging, renaming modules, upgrading dependencies) must carry at least one runtime behavioral evidence item in `verify` (executed command, test run, build); a pure `rg`/static scan may only supplement it and never proves migration complete alone.
- Credential hygiene: `boundary` / `verify` lines and acceptance evidence carry the same secret-exclusion rule as the assignment contract (`references/orchestration.md`) — real credential values never enter package documents, verification command lines, or recorded evidence; inject them via env files / host-side injection, and write examples with placeholders (`<admin-token>`), never real values.
- The optional `id: task-name` gives a task a stable identity (lowercase `task-` prefix); `depends-on` accepts positional IDs (`task_0001`) and explicit IDs. Never delete or reorder checked tasks so positional IDs drift; appended tasks go into a new heading section at the file end with explicit IDs.

## English-title variant

The default init fences stay Chinese (`init_spec_package.py` renders the Chinese default), so an English-language project starts from this variant by copying it verbatim. It carries the same contract with English display titles plus explicit key anchors — optional belt-and-braces (titles alone already resolve every key); they stay as the reference spelling of each key. Keep exactly one language per gated section: a section headed twice in either language counts as a duplicate. Placeholder, verdict, and blocking vocabularies are bilingual with the same semantics: `None`/`无`, `**Result**: pass`/`**验收结果**：通过`, `blocked`/`blocker`/阻塞; §1 and §5.1 field labels accept their English aliases, and `route` plus the task detail keys (`boundary`, `verify`, `depends-on`, `manual:`) were never localized.

### `tasks.md` (English)

```markdown
# [Project Name] - Task Breakdown

## Usage Rules
- every task carries `boundary` and `verify`; a machine task's verify executes the first backtick span as the command
- a task without a verification cannot start; a task that has no executable command writes `verify: manual: <reason>`
- actionable issues found during execution are written back to this package and fixed in the same round
- new packages use `YYYY-MM-DD_<verb>-<object>`; see `references/naming-and-commits.md`
- a verify command must never invoke this package's own check gate (a self-referential command is unsatisfiable under latest-record semantics)

## Stage 1: Implementation
- [ ] Initialize the minimal project skeleton
  - boundary: only the directories, dependencies, and startup skeleton that are strictly required
  - verify: `python3 -m pytest -q tests/test_skeleton.py` (replace with this project's real init verification)
- [ ] Implement core feature A's minimal loop
  - depends-on: task_0001
  - boundary: only the modules this feature's main path needs
  - verify: `python3 -m pytest -q tests/test_core_feature_a.py` (replace with the real test command)
- [ ] Wire the critical path
  - depends-on: task_0002
  - boundary: only the glue the integration needs, no opportunistic refactoring
  - verify: `python3 -m pytest -q tests/test_critical_path.py` (replace with the real integration command)

---

**Progress**: computed by the scripts, never maintained by hand
```

## Success criteria (`spec.md` §6, v2 packages)

`## 6. 成功标准与验证方式` is the acceptance surface for the checklist-free package:

- Every criterion is a checkbox `- [ ] <criterion> -> verify: task_XXXX` naming the task whose `verify` proves it; tick it only after that verification actually ran and passed — same discipline as every other checkbox in the harness.
- `check` and `done` for a checklist-free package require: all §6 criteria checked, all tasks done, and executable evidence — the `evidence: runs` gate when declared, otherwise at least one real command span among the §6 lines. A §6 with no checkboxes, or whose criteria reference nothing verifiable, fails closed: the success-criteria surface must be non-empty and machine-checkable.
- The minimal-review point lives here as one criterion (对照 spec §4「暂不引入」清单在验收记录中列出被拒绝的扩展点或确认无) instead of a boilerplate task.

## Legacy `checklist.md` (v1 packages only)

`init_spec_package.py` no longer renders `checklist.md`. Packages that already carry one keep the exact legacy gates — never rewritten, never regraded:

- Base gates: every checkbox checked and `**验收结果**：通过`.
- `## 验收证据` must fill at least one non-placeholder field among `外部对标` / `脚本验证` / `旧新对比` / `差异边界` / `行为成效`, with one real command under `脚本验证` (script verification), `测试` (tests), or `构建` (build).
- Truncated evidence: output that was truncated, paged, or timed out must be marked `truncated` and re-captured with a narrower scope (filter, single target, longer timeout) until the full relevant output is in evidence; unmarked or un-recaptured truncated output never counts as a passing basis.
- Evidence freshness anchor (optional, Git projects): `- 证据锚点：HEAD <sha> @ <ISO-8601 时间>` under `## 验收证据`; once present, `check_spec_package.py` fails the check with 证据过期需重跑取证 when the project repo's HEAD moved; no anchor keeps the legacy behavior (advisory only). In `evidence: runs` packages the runs worktree fingerprint takes over this duty.
- Verification scope: `### 5.1 验证策略` declares one level — `package` (default), `integration`, or `project`; `check` runs the declared level (a legacy checklist's `验证范围` label must match `spec.md`), and `done` reuses the same scope and evidence.
- Decisive-check line (optional, appears in force): `裁决性检查：<命令> @ <时间>` under `## 验收证据` records the strongest check at the declared verification level; marking it 适用外 requires the factual basis that 该检查在本项目不存在 — 以慢为由 is never a valid reason. An absent line keeps the legacy behavior.
- The optional sections `## 跨载体一致性`, `## 项目结构与文档可信度`, and `## 边界回归` activate additional gates once present: every box must be checked to pass; a row that does not apply is still checked off with an inline `N/A：<理由>` annotation.

## `completion-summary.md`

Generated by `scripts/complete_spec_package.py` — never hand-write a second full template. Archives must contain the v1 `## 问题处置` (issue dispositions):

```json
{
  "version": 1,
  "issues": []
}
```

Field order: delivery conclusion → assumption review → delivery scope → simplification decisions → change boundaries → verification evidence (notes) → verification scope → Git record → AGENTS.md incremental proposal → gate evidence → process metrics (optional) → open items → issue dispositions. Non-empty issues use `--issue-disposition`; `resolved_followup` may only point at an already-archived Development Record.

`## 过程指标` (process metrics) renders only when `complete_spec_package.py` receives at least one `--process-metric` entry (repeatable), placed between `## 门禁证据` and `## 遗留事项`; with no entry the section is absent so the legacy field order is unchanged.

## AGENTS.md proposal and the Module DAG

Distillation is an incremental proposal, not a document pipeline: when a round produces a new reusable project-specific fact, `done` renders it as an `## AGENTS.md 增量提议` diff fence in `completion-summary.md` (`--agents-proposal`, repeatable; no reusable fact records 无). The proposal targets the executing project's own `AGENTS.md` or host-equivalent instruction file, is never applied automatically — landing stays a human decision — and never writes into global carriers (`~/.claude/CLAUDE.md`, user-level `AGENTS.md`, user-level memory). Standalone knowledge documents are no longer produced by default; existing `.spec/docs/YYYY-MM-DD_<slug>_<topic>.md` files stay unchanged as history.

Module DAG: `.spec/architecture/module-index.md`, `module-dag.md`, `module-dag.mmd`. Nodes are modules, not tasks; the graph must be acyclic; task packages reference it and never copy it.
