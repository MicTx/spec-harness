# Templates

Templates are executable contracts in prose. Read only the three init fences below by default. `scripts/init_spec_package.py` parses only the first ` ```markdown ` fenced block of `spec.md` / `tasks.md` / `checklist.md`; `completion-summary.md` is generated by the script, so never hand-write a second full template. Replace every placeholder before execution and keep `boundary`, `verify`, and acceptance evidence tied to a real check.

When changing the init templates, change only these three fences.

## `spec.md`

```markdown
# [项目名称] - 项目范围

## 1. 问题定义
- **项目目标**：一句话描述项目要解决什么问题
- **目标用户**：谁会使用这个产品或系统
- **核心价值**：完成后能持续提供什么价值

## 2. 假设与待确认

### 2.1 已确认事实
- 事实 A

### 2.2 关键假设
- 假设 A

### 2.3 待确认问题
- 问题 A

### 2.4 可选解释与取舍
- 当前选择：xxx -> 理由

## 3. 功能范围

### 3.1 核心功能（MVP）
- [ ] 功能 A：描述

### 3.2 扩展功能
- 无

### 3.3 不在范围内
- 明确列出本轮不做的内容

## 4. 最小实现路径
- 最简单可行方案：xxx
- 暂不引入：xxx
- 不做的抽象/配置化：xxx

## 5. 技术决策
- 技术栈：xxx 或适用外
- 本轮允许改动：xxx
- 本轮不应触碰：xxx
- Git integration branch：`spec/YYYY-MM-DD_<slug>` 或适用外理由

### 5.1 验证策略
- 范围级别：package
- 变更对象：本任务包 boundary 涉及的模块、入口和数据契约
- 快速检查：<变更对象对应的局部测试/静态检查命令>
- 集成检查：适用外：本轮没有直接受影响的跨模块用户路径
- 全项目检查：适用外：本轮不涉及共享基础设施、跨模块契约或发布载荷；由发布门禁统一执行
- 升级触发：只有改动共享基础设施、跨模块契约、构建/依赖、发布载荷，或 package/integration 检查暴露跨边界回归时，才把范围升级并记录理由

## 6. 成功标准与验证方式
- 标准 A -> verify: xxx
- 标准 B -> verify: xxx

## 7. 风险与约束
- 风险点：xxx -> 缓解措施
```

Writing requirements:

- `2. 假设与待确认` (assumptions & open questions) must not be empty; write uncertainties down.
- `4. 最小实现路径` (minimal implementation path) must have at least 3 items and answer "why not more this round".
- Do not put optional governance headings into the default package.

When tasks depend on each other, declare `- depends-on: task_0001, task_0002` (comma-separated positional IDs) under the dependent task. Execution follows dependencies; reordering tasks must keep these IDs in sync. Without a declaration, tasks stay independent.

## `tasks.md`

```markdown
# [项目名称] - 任务拆解

## 使用规则
- 每个任务都要写清楚 `boundary` 和 `verify`
- 如果一个任务没有验证方式，就不能开始
- 发现的可执行问题必须回写本包，并在本轮做完
- 新任务包使用 `YYYY-MM-DD_<verb>-<object>`，详见 `references/naming-and-commits.md`

## 阶段一：澄清与初始化
- [ ] 固化问题定义、关键假设与非目标
  - boundary: 只更新 `.spec/specs/[任务包名]/spec.md`
  - verify: `spec.md` 已写明事实、假设、待确认问题、不在范围内内容和当前 integration branch
- [ ] 从主分支创建独立工作分支
  - boundary: 只执行 Git 分支检查/创建，不改业务文件
  - verify: 当前分支是从 `main`（或显式主分支）创建的非受保护 `spec/YYYY-MM-DD_<slug>` integration branch，或记录非 Git 适用外理由

## 阶段二：核心实现
- [ ] 初始化最小项目骨架
  - depends-on: task_0001, task_0002
  - boundary: 只创建必须目录、依赖和启动骨架
  - verify: 最小启动、构建或初始化命令通过
- [ ] 实现核心功能 A 的最小闭环
  - depends-on: task_0003
  - boundary: 只改该功能主链路所需模块
  - verify: 对应单测、集成测试或手工验证通过

## 阶段三：集成与验收
- [ ] 打通关键链路
  - depends-on: task_0004
  - boundary: 只补集成所需粘合代码，不顺手重构
  - verify: 关键用户路径验证通过
- [ ] 最小化复核点：确认未引入未请求抽象/配置化
  - depends-on: task_0005
  - boundary: 只审查当前任务包相关改动
  - verify: 在验收记录中列出被拒绝的扩展点或确认无
- [ ] 完成验收检查并补齐文档
  - depends-on: task_0005, task_0006
  - boundary: 只更新任务包文档、检查项与验收证据
  - verify: `checklist.md` 达到可判定状态

---

**当前进度**：由脚本计算，无需手动维护
```

Writing requirements:

- Stage names express delivery order. One task + one pair of `boundary` / `verify`.
- The paths and commands above are pre-project examples and authorize nothing for arbitrary projects; replace them with real boundaries and verification commands that prove delivery before execution.
- Run the `verify`-described verification independently before checking a task off; never check off an unrun verification.
- Migration/upgrade tasks (moving, merging, renaming modules or upgrading dependencies) must carry at least one runtime behavioral evidence item in `verify` (an executed command, a test run, a build) — a pure `rg`/static scan may only supplement it and never proves the migration complete on its own.
- Credential hygiene: `boundary` / `verify` lines and acceptance evidence carry the same secret-exclusion rule as the assignment contract (`references/orchestration.md`) — real credential values never enter package documents, verification command lines, or recorded evidence; inject them via env files / host-side injection, and write examples with placeholders (`<admin-token>`), never real values.
- The optional `id: task-name` gives a task a stable identity (a lowercase `task-` prefixed string); `depends-on` accepts both positional IDs (`task_0001`) and explicit IDs. Never delete or reorder checked tasks so positional IDs drift; appended tasks go into a new heading section at the file end with explicit IDs.

## `checklist.md`

```markdown
# [项目名称] - 验收清单

## 假设与范围对齐
- [ ] 无阻塞性待确认项；如有待确认项，已明确标记无需阻塞/适用外并给出理由
- [ ] 范围内/范围外与实现一致
- [ ] 本轮发现的可执行问题已回写任务包并完成，未甩给用户

## 简洁性
- [ ] 没有未请求的扩展、抽象或配置化
- [ ] 当前方案保持最小可行

## 变更边界
- [ ] 每项改动都能追溯到明确任务
- [ ] 没有无关重构或顺手清理

## 功能完整性
- [ ] MVP 功能全部实现
- [ ] 边界条件已处理
- [ ] 错误处理符合预期

## 测试与验证
- [ ] 核心逻辑有测试或等价证据
- [ ] 关键路径已验证

## 文档同步
- [ ] 受影响文档已更新，或记录适用外
- [ ] `spec.md` / `tasks.md` / `checklist.md` 已同步

## 部署验证（如适用）
- [ ] 本地运行正常，或已记录适用外理由
- [ ] 构建成功，或已记录适用外理由

## 边界回归
- [ ] 越界负样本：boundary 外改动会被识别或回滚，未混入交付（本轮不适用时记 `N/A：<理由>` 后勾选）
- [ ] 顺序交换负样本：交换无依赖任务或调换检查节顺序，验收结论不变（本轮不适用时记 `N/A：<理由>` 后勾选）
- [ ] 旁路负样本：不存在绕过 `verify` 的完成入口，未运行的验证一律视为未通过（本轮不适用时记 `N/A：<理由>` 后勾选）

## 验收证据
- 裁决性检查：<命令> @ <时间>
- 验证范围：<package|integration|project>；实际执行命令必须属于该范围
- 外部对标：以 task package 状态机为真，fresh package 不得直接进入实现态
- 脚本验证：
- 旧新对比：
- 差异边界：
- 行为成效：
- 构建：
- 测试：
- 手工验证：

---

**验收结果**：待修复
```

Writing requirements:

- Base gates: every checkbox checked and `**验收结果**：通过`.
- `## 验收证据` (acceptance evidence) must fill at least one non-placeholder field, with one real command under `脚本验证` (script verification), `测试` (tests), or `构建` (build).
- Truncated evidence discipline: command output that was truncated, paged, or timed out must be marked `truncated` and re-captured with a narrower scope (filter, single target, longer timeout) until the full relevant output is in evidence; an unmarked or un-recaptured truncated output never counts as a passing basis — success is not completeness.
- Evidence freshness anchor (optional, Git projects): record `- 证据锚点：HEAD <sha> @ <ISO-8601 时间>` under `## 验收证据` when evidence is captured. Once present, `check_spec_package.py` fails the check with 证据过期需重跑取证 when the project repo's HEAD has moved; no anchor keeps the legacy behavior (advisory only).
- Verification scope: every new package declares `### 5.1 验证策略` with one level: `package` (default, changed modules and their focused checks), `integration` (package checks plus directly affected cross-module paths), or `project` (the full project suite). `package` requires a real quick check; `integration` additionally requires a real integration check; `project` additionally requires a real full-project check. `check` runs the declared level; a project README's full suite is not automatically required for a package-level change. Upgrade to `project` only for shared infrastructure, cross-module contracts, build/dependency, release-payload, or observed cross-boundary regressions, and record the reason. The machine gate checks that the checklist's `验证范围` label matches `spec.md`; reviewers judge whether the recorded command fits the declared fields. `done` reuses the same scope and evidence; it does not silently widen the test run.
- Decisive-check line (optional, appears in force): `裁决性检查：<命令> @ <时间>` under `## 验收证据` records the strongest check at the declared verification level, actually run at least once before the result is written down; an absent line keeps the legacy behavior. Marking this line 适用外 (out of scope) requires the factual basis that 该检查在本项目不存在 — package.json / Makefile / CI 配置 / README must have been searched with the result noted; 以慢为由 (too slow) is never a valid reason.
- The optional sections `## 跨载体一致性` (cross-carrier consistency), `## 项目结构与文档可信度` (structure & documentation trust), and `## 边界回归` (boundary regression) activate additional gates once present in a checklist: every box must be checked to pass; a row that does not apply to the round is still checked off with an inline `N/A：<理由>` annotation. The init template ships `## 边界回归` by default; the other two are added per package when needed, never by default.

## `completion-summary.md`

Generated by `scripts/complete_spec_package.py` — never hand-write a second full template. Archives must contain the v1 `## 问题处置` (issue dispositions):

```json
{
  "version": 1,
  "issues": []
}
```

Field order: delivery conclusion → assumption review → delivery scope → simplification decisions → change boundaries → verification evidence → verification scope → Git record → knowledge distillation → gate evidence → process metrics (optional) → open items → issue dispositions. Non-empty issues use `--issue-disposition`; `resolved_followup` may only point at an already-archived Development Record.

`## 过程指标` (process metrics) is an optional section between `## 门禁证据` and `## 遗留事项`: it renders only when `complete_spec_package.py` receives at least one `--process-metric` entry (repeatable), carrying check-loop measurements such as check rounds, rework counts, and human-escalation marks (`转人工`); with no entry passed the section is absent so the legacy field order is unchanged.

## `.spec/docs` and the Module DAG

Knowledge documents: `.spec/docs/YYYY-MM-DD_<slug>_<topic>.md`, recording only reusable conclusions, never executable tasks. They stay inside the executing project's own `.spec/` tree; global carriers never receive distillations.

Module DAG: `.spec/architecture/module-index.md`, `module-dag.md`, `module-dag.mmd`. Nodes are modules, not tasks; the graph must be acyclic; task packages reference it and never copy it.
