# Templates

`scripts/init_spec_package.py` renders the first ` ```markdown ` fence under each `## \`<file>\`` heading: `spec.md` (LITE, default), `spec.full.md` (FULL, rendered as `spec.md` with `--workflow full`) and `tasks.md`. `completion-summary.md` is generated by `complete_spec_package.py`. Change only these fences when changing init output.

Headings are matched by stable keys (`scripts/spec_package_support.py`, `SectionKey`): the Chinese title, its English alias, or an anchor such as `<!-- spec:open-questions -->`. New packages are written in English; the Chinese aliases exist so legacy packages keep parsing. Replace every placeholder before `run`.

## `spec.md`

```markdown
# [Project Name] - Project Scope

<!-- spec-format: 2 -->

## 1. Problem Definition
- **Goal**: one sentence describing the problem this project solves

## 2. Assumptions And Questions

### 2.2 Key Assumptions
- Assumption A

### 2.3 Open Questions
- [ ] Question A

## 3. Scope

### 3.3 Out of Scope
- explicitly list what this round will not do

## 4. Minimal Implementation Path
- simplest viable approach: xxx

## 5. Technical Decisions
- Workflow: LITE
- Evidence protocol: evidence: runs
- Git integration branch: `spec/YYYY-MM-DD_<slug>` or not applicable

### 5.1 Verification Strategy
- scope level: package
- quick check: <local test or static check command for the changed area>

## 6. Success Criteria And Verification
- [ ] Criterion A met -> verify: task_0001

## 7. Risks And Constraints
- None
```

LITE rules:

- `Goal` is one sentence; `Key Assumptions` lists only premises whose failure would change the plan; `2.3` lists open questions or the single line `- none`.
- `5.1`: `scope level` is `package` (default), `integration` (also fill `integration check`) or `project` (also fill `integration check` and `full-project check`). `quick check` is a real command.
- Each `## 6` criterion names the task whose `verify` proves it; tick it only after that verify passed.

## `spec.full.md`

```markdown
# [Project Name] - Project Scope

<!-- spec-format: 2 -->

## 1. Problem Definition
- **Goal**: one sentence describing the problem this project solves
- **Target users**: who will use this product or system
- **Core value**: the lasting value delivered once complete
- **Literal ask**: <verbatim request>
- **Stated purpose**: <purpose|unknown>
- **Inferred outcome**: <result>; confidence: <high|medium|low>; evidence: <source>
- **Constraints and exclusions**: <constraints|unknown>
- **Trade-off preference**: <speed|quality|cost|maintainability|unknown>

## 2. Assumptions And Questions

### 2.1 Confirmed Facts
- Fact A

### 2.2 Key Assumptions
- Assumption A

### 2.3 Open Questions
- [ ] Question A

### 2.5 Falsified Paths
- None

## 3. Scope

### 3.1 Core Features (MVP)
- [ ] Feature A: description

### 3.3 Out of Scope
- explicitly list what this round will not do

## 4. Minimal Implementation Path
- simplest viable approach: xxx
- not introducing yet: xxx
- abstractions/configurability not built: xxx

### 4.1 Option Ladder
- B0 | literal ask | <compare>
- B1 | minimal change | <compare>

Recommendation: B0 because <reason>. Flips if A1 is FALSIFIED.

## 5. Technical Decisions
- Workflow: FULL
- Stack: xxx or not applicable
- Evidence protocol: evidence: runs
- Allowed changes this round: xxx
- Do not touch this round: xxx
- Autonomy: medium
- Git integration branch: `spec/YYYY-MM-DD_<slug>` or not applicable

### 5.1 Verification Strategy
- scope level: package
- UI surface: <changed|unchanged>
- quick check: <local test or static check command for the changed area>

<!-- spec:correction-log -->
### 5.5 Correction Log
- none.

<!-- spec:deviation-log -->
### 5.6 Deviation Log
- none.

## 6. Success Criteria And Verification
- [ ] Criterion A met -> verify: task_0001

## 7. Risks And Constraints
- Risk: xxx -> mitigation
```

FULL adds, on top of LITE:

- Key assumptions as `A<n> | statement | kind: intent|system|external | evidence | CONFIRMED|UNVERIFIED|FALSIFIED | if false: <impact>`.
- `4.1`: `B0` is the literal ask, `B1` the smallest useful change; add `B2`/`B3` only for a materially different option. The recommendation names its flip assumption.
- `UI surface: changed` requires `- Browser check: \`<command>\`` repeated in a machine task `verify`.
- `5.5` gets one row (`| round | approach | result | new information |`) per failed correction round; a round without new evidence means change strategy, a second one goes to the owner. `5.6` records deviations from the literal ask as `D<n> | literal ask | actual | reason | reversibility | authority`.
- External facts that can change the plan (versions, API behavior, pricing) are recorded with a source URL and date under an optional `### 2.6 External Facts`.

### Pending questions

`2.3` has one markup: an open question is a plain `- [ ]` line; an answered one is `- [x]` plus `| answer: <conclusion>`.

```text
- [ ] Which local format should we use?
- [x] Use the local parser | answer: keep the existing JSON parser
- [ ] [decision] May we publish the results?
```

`[decision]` marks the questions that require user authority (permission, irreversible actions, preferences, external dependencies): it closes only with both `answer:` and `| authority: user:<reference>`. A non-placeholder answer closes any other question; Git writes, credentials, global configuration, publication and destructive external actions are always `[decision]`. The single line `- none` means there are no pending questions.

## `tasks.md`

```markdown
# [Project Name] - Tasks

## Usage Rules
- Every task declares `boundary` (what may change) and `verify` (the first backticked value is the executable command; when machine verification is impossible, write `verify: manual: <reason>`)
- Add `depends-on: task_0001` when order matters; tick a task only after its verify ran
- Append newly discovered executable problems as new tasks and finish them this round

## Phase 1: Implementation
- [ ] Deliver the smallest end-to-end slice of core feature A
  - boundary: only the modules on that feature's main path
  - verify: `python3 -m pytest -q tests/test_core_feature_a.py` (replace with the real project test command)
- [ ] Connect the critical path
  - depends-on: task_0001
  - boundary: only the glue the integration needs; no opportunistic refactors
  - verify: `python3 -m pytest -q tests/test_critical_path.py` (replace with the real integration command)
```

Task rules:

- One task, one passable verification. A `verify` command carries what it needs to run (directory, preconditions); a template command left in place fails on purpose.
- `verify` never calls this package's own check gate. Real credentials never appear in `boundary`, `verify` or evidence; use placeholders such as `<admin-token>`.
- Optional `id: task-name` gives a stable identity. Never reorder checked tasks; append new ones in a new section with explicit ids.
- Evidence: `python3 scripts/spec_verify.py run --root <project> --slug <slug> --all` records `runs.jsonl`; `check` and `done` need each machine task's latest record to pass on the current worktree. Rerun `--all` after any change.

## Success criteria

The `## 6.` section is the acceptance surface (legacy packages title it `## 6. 成功标准与验证方式`; the parser keys on the numeric prefix, and the English alias is `## 6. Success Criteria And Verification`): every criterion is `- [ ] <criterion> -> verify: task_XXXX`, and `check`/`done` require all criteria ticked, all tasks done and passing runs evidence. An empty §6 fails.

Legacy v1 packages that still carry `checklist.md` keep their checklist gates until migrated; `init` never renders one.

## `completion-summary.md`

Generated by `complete_spec_package.py`; it must contain the v1 issue-disposition JSON (`{"version": 1, "issues": []}`, non-empty via `--issue-disposition`). New summaries title it `## Issue Disposition`; records that use the legacy `## 问题处置` heading stay readable. Distillation is an optional agents-increment proposal diff fence (`--agents-proposal`), never applied automatically and never written to global or user-level files.
